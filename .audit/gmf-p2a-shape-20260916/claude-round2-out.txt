TOP 3 BRUTAL FINDINGS
1. The migration evidence contradicts itself. A leftover view named after a v2 table counts as "unexpected presence", which the state policy rejects before any DDL, so the injected failure never reaches the rollback path. The version check is also not required to run inside BEGIN IMMEDIATE, so two processes can both see v1 and the loser fails instead of converging. And base v1 writes its table and user_version in separate steps, so a crash between them leaves a real v1 file that gets rejected as malformed.
2. The schema does not enforce the P1 rules it maps to. UNIQUE(EffectAttemptId, TerminalSequence) accepts a second, conflicting terminal (P1-C112). No trigger blocks UPDATE or DELETE (P1-C108/C116). PendingEffects has no resolution state, so P2C would need a v3 migration. Settlements has no amount/currency pairing CHECK. No test proves any rewrite is rejected.
3. The governance wording overreaches. Rollback deletes *.db, *-wal and *-shm across the whole OS temp directory, which breaks the spec's own ban on globs and could destroy unrelated databases. The loop-directive re-pin rests only on the coordinator's own "drift ACCEPTED" ruling. The "Allowed Files: may be created or changed" heading still lists agent-skills paths.

TOP 3 MOVES
1. Classify the version state inside BEGIN IMMEDIATE. Inject the failure with a test-only hook that throws after the first v2 CREATE. Treat user_version=0 plus an exact v1 table as canonical v1. Start both initializers from one shared file-based barrier.
2. Add BEFORE UPDATE/DELETE RAISE(ABORT) triggers to all v2 tables. Add a partial unique index that allows one terminal per attempt. Add the Settlements pairing CHECK. Choose an append-only pending-resolution row. Test each rejection with raw SQL.
3. Clean up only temp database paths the test itself recorded. Cite a human or recorded authority for the loop-directive re-pin. Move the agent-skills files under a "Shaping outputs (no builder authority)" heading.
