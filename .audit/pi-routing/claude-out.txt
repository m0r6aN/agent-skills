**Verdict: don't let Pi choose the model automatically.**

- **Policy conflict:** Foreman's routing policy already rejects routers, choosing a different model without saying so, and automatically moving to a pricier model. Its own routing check is the only router. Pi's `pi-model-auto` upgrades to stronger models and never steps back down within a session, which the policy forbids (`automatic_cost_escalation_allowed: false`).
- **Providers aren't approved:** OpenRouter and OpenCode appear nowhere in `routing-policy.yaml`. Foreman would therefore reject every model in the draft, even for public data.
- **Role rules break:** The coordinator and verifier must run on the top-tier models (Fable or Opus). Claude 3.5 Sonnet and GPT-4o-mini don't qualify. Because `pi-model-auto` keeps one model for the whole session, it also breaks the rule that a verifier must run as a separate instance on a different model from the coordinator.
- **The audit record could be wrong:** Foreman records the model it picked. If Pi, or OpenRouter's own fallback, then runs a different model, that record is false.

**What to do instead:**
1. For each task, Foreman passes Pi one exact model, and the worker's `enabledModels` lists only that model.
2. Add OpenRouter or OpenCode only as validated worker entries in `routing-policy.yaml`: marked third-party, public data only, pinned model versions, and OpenRouter's fallback turned off.
3. Foreman sets the thinking level for each role. Remove the draft's global "minimal" default.
4. Run `pi-auto-router` only in shadow mode, which logs what it would pick without acting. Its output is advisory only.
5. Add a check after each run that fails the task if the model that actually answered isn't the one Foreman picked.
