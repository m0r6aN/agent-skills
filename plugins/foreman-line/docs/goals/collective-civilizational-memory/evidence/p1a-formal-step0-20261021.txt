### Frozen v2 validation and trust table

The v2 serialized fixture uses snake_case v4 fields, `schema_version: shards/2.0`, existing ReceiptAnchor aliases inside receipt references, timezone-explicit UTC event times and finite numeric values. Producer input cannot authoritatively set scoped IDs, approval or verification results. Validation errors are non-content-bearing structured field/code diagnostics, never secret-bearing payload echoes.

For all nine canonical MemoryKinds, direct source tiers map as follows: verified_receipt -> RECEIPT; explicit_human_directive and deterministic_code_or_event -> RAW_EVIDENCE; unverified_candidate -> SUMMARY. The source tier requires its own trusted source/proof admission; merely supplying it or a receipt pointer does not establish it. `corroborated_causal` and `uncorroborated_causal` are valid only for Causal and map to CAUSAL_RECORD. `distilled_verified` is valid only for Semantic/Procedural and maps to SEMANTIC_MEMORY/PROCEDURAL_MEMORY respectively. Reject other combinations; enumerate the full cross-product, including rejection rows, in fixtures. Embedding projections remain derivative artifacts, not a new memory kind or evidentiary shard.

Tier numbers are default direct-source weights. Derived effective score is `min(0.70, 0.90 * min(parent effective scores))`; require a nonempty parent set and finite scores in [0,1]. All eligible high-trust parents (>=0.85) permit Semantic/Procedural distilled_verified; other derived candidates retain unverified_candidate. Derivation cannot inherit RECEIPT/RAW_EVIDENCE standing. Promotion is separately receipt-governed and never turns a child into an execution receipt. Inheritance selection uses effective score AND required tier/evidence, never numeric score alone.

Distinguish untrusted producer assertions from authoritative resolved parent inputs. A submitted parent reference, score, tier or verification flag is not proof: effective scores and required evidence derive from parent records resolved under the applicable identity, current-scope and authentication contracts. Specify fail-closed behavior for missing, invisible, unauthenticated or substituted parents and producer-injected scores/tiers. Mathematical positive fixtures represent already-resolved trusted inputs, separately from producer-payload negatives. P1A defines this contract/interface, not a live resolver or a qualified positive producer.

### State, visibility and deletion contract

- Active/buffered accept all three validity states; archived is cold; superseded requires a real non-null replacement; purged retains only the scoped tombstone/proof metadata. Retention is independent of epistemic validity. `derived_decay_state` exists only in response projections at explicit `as_of`.
- Parent loss: sole/all parents lost -> surviving child archived+contested with invalidation reason; partial loss -> contested, preserving existing archival state (including buffered/archived/superseded). Purged child remains unchanged. Revalidation cannot implicitly restore archived children. Explicit replacement preserves lineage. Symbol changes stale validity; correction/failure contests validity. Signals older than/equal to last_revalidated_at are no-ops; terminal purges never reverse. Test equality, repeated signals and all surviving-parent archival combinations.
- Buffer evidence contains entered-at plus a success-counter snapshot/event equivalent. At most one archival transition per sweep. A new deduplicated verified success reactivates buffered (preserving validity); archived requires explicit restoration. Preserve strict 0.50/0.25 inequalities and event-time semantics from S07.
- Plane-A has tenant/profile/role/scope binding using existing visibility law, endpoint integrity and immutable versioned node IDs. Preserve the v4 edge hash recipe with versioned endpoint IDs and temporal intervals [start,end). Retain separate logical artifact identity. Current authorization applies at every historical hop and both endpoints; never infer sharing from common tenant.
- Recall graph depth <=2. Read APIs default depth2/max3; request budgets 1000 returned nodes/4000 edges/10000 examined visible edges. Specify deterministic cursors bound to query/as_of/authorization, per-page reauthorization, cycle deduplication, explicit truncation and no hidden counts/dangling endpoints. These are API contracts, not implemented traversal here.
- Document the complete S10 routing table and whole-warning/conflict-group budget protocol; source citations require existence/scope/identity/proof validation, not only post-trim membership.
- Define deletion milestones (authoritative fence, derivatives, keys, coverage), durable idempotent cleanup/invalidation jobs, batch write fencing, retry/reconciliation and non-content evidence. P3 owns minimal Wave-1 purge propagation; P6 extends other triggers. A SQL transaction cannot atomically delete Qdrant or destroy external keys.
- Define a key-custody adapter requirement with scoped key reference, authorized idempotent destruction operation, status/evidence and backup/replica coverage. Do not select a provider or claim erasure until separately qualified; plaintext/key-bearing backups keep completion blocked. HMAC scrubber keys are not shard erasure keys.
- Document S11 civic caution wire semantics and S12 fail-closed scrubber boundary; no live enforcement or scrubber implementation here.

### S05 — Lexical retrieval and RRF

Recommend built-in PostgreSQL `ts_rank_cd`, not an unqualified BM25 claim.
For one-based channel ranks and k=60, normalize as:

`rel = sum(1 / (60 + rank_c)) / (3 / 61)`.

An absent channel contributes zero; do not renormalize by the number of present
channels. Rank 1 in all three channels gives 1; rank 1 in one channel gives 1/3;
rank 2 in all three gives 61/62. Use up to 200 visible candidates per channel,
with scope filtering before ranking/limits. Positive relevance requires
`ts_rank_cd > 0`, positive cosine similarity, or a visible graph match within two hops.
Native channel ties and final composite ties resolve by shard ID ascending.
The channel limits and formula belong to pinned v2 parameters; performance
calibration cannot silently mutate them.

### S06 — Tier classification versus inherited numeric trust

Recommend preserving the exact mixed-parent formula on a separate effective
`provenance_score`: `min(0.70, 0.90 * min(parent effective scores))`.
The tier table's numeric values are source/default weights, not a rounding grid
for descendants. A 0.20 parent produces 0.18, not 0.20; a 0.40 parent produces
0.36, not a fabricated tier promotion. Tier labels retain their categorical
meaning and do not rise merely because of a computed score.

Use `distilled_verified` only for Semantic/Procedural children of sources meeting
its >=0.85 source condition; otherwise derived candidates remain
`unverified_candidate` unless a specific verified promotion contract applies.
Non-evidentiary children never acquire Receipt/RawEvidence standing from their
parents or from the receipt approving their promotion.

The P1A draft must enumerate valid tier/kind combinations and deterministic
AuthorityClass results, rejecting unsupported combinations rather than guessing.
Receipt verification remains an independent requirement; neither labels nor
numeric trust are receipt proofs. This recommendation explicitly clarifies the
relationship between D3's categorical ordering and numeric retrieval weight.

### S07 — Retention bookkeeping and delayed sweeps

Recommend recording buffer-entry time and a verified-success counter snapshot
(or equivalent durable events); cumulative lifetime success is not a test of

preserves its epistemic validity. Archived shards require explicit restoration.

Apply at most one archival transition per sweep per shard. A late sweep buffers
an active record first; a later sweep may archive it. Preserve strict threshold
inequalities: an unreinforced S=3 record is active at day 27 and first buffers

### S10 — Total briefing routing and budget safety

### S11 — Caution contracts and explicit enforcement dependency

Recommend `max(policy floor, role baseline oversight, domain caution floor,
action-required floor)` using existing Collective `AgentOversightLevel` values
Routine/Elevated/Critical. The numeric oversight baseline belongs to existing
`AgentOversightProfile`; `AgentConstraintProfile` remains constitutional limits,
not a second independently invented oversight scale.

A new verified domain failure increases each boost by 0.10 (cap 2.0), raises the
caution floor one level (cap Critical), and clears the success streak. Ten
verified successes from ten distinct task keys with no intervening failure
lower the caution floor one level toward baseline and each boost by 0.10 toward
1.0, consuming that streak. Operator reset returns the caution additions to
baseline/1.0 only with current operator authorization and a verified decision
receipt bound to role/domain/reset effect. Neither path lowers another policy,
action or role constraint. Missing/unverifiable enforcement state cannot widen
a previously required floor.

Use an authoritative per-role/domain committed sequence, idempotent receipt
consumption, and distinct-task accounting. Late failures always tighten; success
events at/before the latest failure event time cannot count toward recovery.
Concurrent updates/resets serialize with version checks. Emit audit evidence for
accepted/rejected transitions. Profile versions are explicit scoring inputs;
boost application is frozen/versioned, not mutable hidden gravity parameters.

### S12 — Deletion protocol, key coverage and scrubber boundaries

Recommend a governed Postgres transaction that commits the authorized tombstone,
clears searchable payloads, fences reads, and writes durable idempotent cleanup
and descendant-invalidation jobs. A signed Purge event is delivered through the
durable event path, not falsely described as atomically signed by an external
service. Workers retry/reconcile configured derivative indexes, outbox/payload
copies and dependent children; the minimal purge-driven invalidation required
by Wave 1 belongs to P3, not deferred wholesale to P6. Pending descendants cannot
be served as unqualified valid knowledge while invalidation is incomplete.

Freeze separate observable milestones: authoritative tombstone/read fence,
derivative cleanup, key destruction, and verified full-coverage completion.
Failures retain pending/failed coverage state and retry evidence. Completion
requires a stable inventory of copies and a governed import-batch fence so a
concurrent/replayed writer cannot recreate deleted payloads or append unnoticed
to a retracted batch. Preserve minimal non-content receipt/tombstone evidence;
do not preserve raw payloads in audit logs as an exception to deletion.

For genuine cryptographic erasure, require per-shard erasure key material under
external key custody (separate from HMAC scrubber keys), and evidence that no
recoverable key or plaintext survives in replicas, backups, caches or derivative
stores. An encrypted database or a backed-up wrapped key alone is insufficient.
P1A defines the key-custody adapter requirements and coverage state; no key-store
provider or claim of an existing destruction capability is elected here. P3's
crypto-effect implementation remains blocked until a qualified existing Keon
key-management integration and its backup/replica destruction or expiry contract
are independently accepted. Plaintext historical/derivative backups keep full
completion blocked until their cleanup/expiry is verified; do not claim instant
or retrospective cryptographic erasure.

Scrub all persisted textual surfaces (including graph metadata, errors and
logs) in memory before durable enqueue. A fixture path never exempts a secret:
only explicit known synthetic values with positive fixture evidence may be
classified synthetic. Raw credentials never enter Plane-B shards or queues.
Keep original code parsing in bounded memory where required; sanitized output
is the only durable payload. HMAC rotation breaks correlation but is not a
complete forward-secrecy design.

These choices will be expressed as foundation contracts and deterministic
fixtures, not permission for builders to discover an architecture. Downstream
integration/key-service gates remain explicit and do not prevent bounded local
foundation work or justify claiming the overall initiative ready.

   ## 3. Locked Architectural Decisions (`D1–D15`)

   These decisions are pre-ratified by the Owner for Charter creation. Every biological inspiration is paired with its canonical engineering name.

   ### D1 — Two-Plane Topology & Unified `envelope/taxonomy.py` State Machine
   Separate storage into two linked planes inside Cortex Postgres with zero duplicate enums:
   - **Plane A (`artifact_nodes` & `graph_edges` — Structural & Artifact Graph):** Stores repositories, commits, files, AST symbols (`function`, `class`,
 `interface`, `module`), document sections, and conversation episode pointers. Node validity is `[observed_at, superseded_at)` and edge validity is
 `[valid_from, superseded_at)` for exact `as_of` replay (INV-4). Every edge has a deterministic `edge_id = 'edge_' || sha256_hex(canonical_json({tenant_id,
 source_id, source_kind, target_id, target_kind, edge_kind, valid_from}))`.
   - **Plane B (`shards` — Distilled Memory Shards):** Each record carries two persisted orthogonal status axes plus one derived retention projection in
 `envelope/taxonomy.py`:
     1. **Persisted Storage/Archival Axis (`ArchivalStatus`):** `{active, buffered, archived, superseded, purged}`.
     2. **Persisted Epistemic Validity Axis (`ValidityStatus`):** `{valid, contested, stale_code_dependency}` (using `'valid'` so no value collides with
 `DecayState.FRESH = 'fresh'`).
     3. **Derived Retention Projection (`DecayState`):** Pure function of $R_{\text{FSRS}}(m, t)$ at query time $t$ (never stored as a mutable column):
        - `DecayState.FRESH` (`'fresh'`): $R_{\text{FSRS}}(m, t) \ge 0.90$ ($\Delta t \le S_m$)
        - `DecayState.DECAYING` (`'decaying'`): $0.50 \le R_{\text{FSRS}}(m, t) < 0.90$ ($S_m < \Delta t \le 9 S_m$)
        - `DecayState.STALE` (`'stale'`): $0.25 \le R_{\text{FSRS}}(m, t) < 0.50$ ($9 S_m < \Delta t \le 27 S_m$)
        - `DecayState.EXPIRED` (`'expired'`): $R_{\text{FSRS}}(m, t) < 0.25$ ($\Delta t > 27 S_m$)
   - **Allowed Cross-Product:**
     - `archival_status IN ('active', 'buffered')`: `validity_status` may be `'valid'`, `'contested'`, or `'stale_code_dependency'`.
     - `archival_status == 'superseded'`: resolved replacement (`superseded_by` non-null); ineligible for briefings and inspectable via the lineage API.
     - `archival_status == 'archived'`: cold tier (excluded from standard hot recall; inspectable by ID/audit).
     - `archival_status == 'purged'`: cryptographically shredded tombstone (excluded from all recall, skipped prior to `verify_record_identity`).

   ### D2 — Memory Kinds & Rejection Reason Gate
   Extend `envelope/taxonomy.py::MemoryKind` so Plane-B records classify into: `Episodic`, `Semantic`, `Procedural`, `Causal`, and `Repulsive`
 (**Failure-Avoidance Marker** / *Negative Stigmergy*), while retaining `Narrative`, `Evidentiary`, `Derived`, `Reference` for envelope compatibility.
   - **Rejection Gate (Preserving Dissent vs. Failure):** A rejected proposal (`ProposalLineageTransition`) or failed outcome mints a `Repulsive` shard
 **only** when `rejection_reason_class` is in `{'failed_verification', 'violated_invariant', 'runtime_regression', 'security_boundary_breach'}` and is
 anchored to a receipt or test failure. Proposals rejected for `'out_of_scope'`, `'deferred_timing'`, `'budget_cap'`, or `'policy_preference'` are stored as
 `Episodic` dissent records and **never** mint `Repulsive` markers.

 from `(provenance_tier, memory_kind)` so the two never drift (while preserving `AuthorityClass.is_evidentiary` for INV-5 verification gates):

   | Canonical `provenance_tier` | `Prov(m)` | Derived `AuthorityClass` | Evidentiary (`INV-5`) | Description |
   |---|---|---|---|---|
   | `verified_receipt` | `1.00` | `AuthorityClass.RECEIPT` (100) | `True` | Cryptographically verified execution/approval receipt (`rcpt_`). |
   | `explicit_human_directive` | `1.00` | `AuthorityClass.RAW_EVIDENCE` (90) | `True` | Authenticated human operator directive. |
   | `deterministic_code_or_event` | `0.85` | `AuthorityClass.RAW_EVIDENCE` (90) | `True` | Deterministic AST/git extraction or structured

   | `corroborated_causal` | `0.75` | `AuthorityClass.CAUSAL_RECORD` (70) | `False` | `Causal` shard corroborated by $\ge 1$ subsequent verified `outcome`

   - **Mixed-Lineage Rule:** For any distilled shard derived from parent set $P$, initial provenance is $\text{Prov}(m) = \min(\,0.70,\; 0.90 \times \min_{p

 `SUPERSEDED_BY` / `correction` link resolves the conflict by transitioning the older shard to `archival_status = 'superseded'` (ineligible for briefings,
 reachable via lineage API); (b) if unlinked/unresolved, both remain `archival_status = 'active'`, while the later explicit `observed_at` has

     $$S(m, q, t) = w_{\text{rel}} \cdot \widehat{\text{Rel}}(m, q) + w_{\text{prov}} \cdot \text{Prov}(m) + w_{\text{util}} \cdot \text{Util}(m) +
 w_{\text{temp}} \cdot R_{\text{FSRS}}(m, t)$$

 \text{shard\_id ASC}$; excluded from graph rank if $d > 2$), scaled by $3 / (k_{\text{RRF}} + 1)$.
     - $R_{\text{FSRS}}(m, t) = \left(1 + \frac{\max(0, t - t_{\text{last}})}{9 \cdot S_m}\right)^{-1} \in (0, 1]$: FSRS v4 power-law retrievability where

     - $\text{Util}(m) = \tanh(\alpha \cdot u_m) \in [0, 1)$: with $\alpha = 0.35$ and $u_m$ = deduplicated `verified_success_uses` per `(task_key,

 unreinforced)
     - **Stability Growth Curve (Verified by P1 Simulation Test):** On each new verified successful use at time $t$:
       $$S_m' = S_m \cdot \left(1 + \beta_{\text{gain}} \cdot (1 - D_m) \cdot S_m^{-0.2} \cdot \left(0.25 + 0.75 \cdot (1 - R_{\text{FSRS}}(m,

       with $\beta_{\text{gain}} = 1.20$. P1 must include a deterministic simulation test asserting both the 7-day/30-day reinforcement growth curve AND the

   ### D5 — Dependency-DAG Invalidation (*Honeybee Stop Signals*) & Multi-Parent Retraction Rules
   - **Triggers:** (1) A git commit changing or deleting a Plane-A **symbol node's `content_hash`** (file-level whitespace/unrelated edits do not fire
 signals), (2) an operator `correction` event, (3) a verified `outcome=failure` receipt contradicting a `Procedural` or `Causal` shard, or (4) a parent
 shard purge/retraction.
   - **Reverse-Edge Bounded & Idempotent Traversal:** Traverses **incoming (reverse-direction)** `MENTIONS_SYMBOL` edges (`shard → symbol`, traversed from
 changed `symbol` back to dependent `shard`) and **incoming (reverse-direction)** `DERIVED_FROM` edges (`child_shard → parent_shard`, traversed from
 invalidated `parent_shard` to `child_shard`) up to `max_depth = 3`. Each signal carries `signal_occurred_at`. If a target shard has `last_revalidated_at >=
 signal_occurred_at`, the signal is a no-op. Otherwise:
     - Code symbol changes transition target shards to `validity_status = 'stale_code_dependency'`.
     - Corrections and failure receipts transition target shards to `validity_status = 'contested'`.
     - **Parent Retraction/Purge Rule:** If a derived shard's **only** parent is purged/retracted, the child transitions to `archival_status = 'superseded'`
 and `validity_status = 'contested'`. If a derived shard has **multiple parents** and at least one parent remains `active`, the child stays `archival_status
 = 'active'` and transitions to `validity_status = 'contested'`.

   ### D6 — Domain Caution Priors (*Trained Immunity / Epigenetic Role Profiles*) & Receipt-Anchored De-escalation
   Each role/lineage holds a versioned `EpigeneticRoleProfile` keyed by `domain_tag`:
   - **Cortex Responsibility (Advisory):** Increments domain caution weights (`repulsive_boost ∈ [1.0, 2.0]`, `causal_boost ∈ [1.0, 2.0]`,
 `recommended_oversight_floor`) on verified failure receipts in that domain.
   - **Enforcement Owner:** **Keon Gateway and Keon Collective** consume `recommended_oversight_floor` as an advisory tightening-only floor.
   - **Receipt-Anchored De-escalation (Preventing Role Ossification):** `recommended_oversight_floor` may step down toward the role's baseline
 `AgentConstraintProfile` **only** via two receipt-anchored paths:
     - **D6(a) Explicit Operator Reset:** `POST /v1/roles/{role_id}/epigenetic-reset` carrying a mandatory operator Decision Receipt (`rcpt_`).
     - **D6(b) Earned Outcome Decay:** $N = 10$ consecutive verified `outcome=success` receipts (`rcpt_`) in that `domain_tag` across **10 distinct

   ### D7 — In-Memory Pre-Outbox Privacy Scrubber & Code Allowlists

   ### D8 — Budgeted Checkpoint Semantic Extraction & CI Determinism

"""Authority and memory taxonomies for the Universal Evidence Memory Envelope.

These enums classify a memory-like record along two orthogonal axes:

* ``AuthorityClass`` — *evidentiary standing*. How much trust a record may
  command. Cortex is evidentiary memory: raw evidence and receipts are stronger
  than semantic memory, and derived retrieval artifacts (summaries, embedding
  projections) are the weakest — traceable and disposable. Authority is ordered.
* ``MemoryKind`` — *cognitive form* (GMMS memory type). What shape the content
  takes. Unordered; carries no trust weight.

Doctrine alignment (LANE-00):
  INV-5 — Cognitive records are never execution receipts and never satisfy
  verification paths. ``can_serve_as`` enforces that a derived class can never be
  treated as ``Receipt`` or ``RawEvidence``.
"""

from __future__ import annotations

from enum import Enum
from typing import FrozenSet


class AuthorityClass(Enum):
    """Evidentiary standing of a record, ordered by ``rank`` (higher = stronger).

    ``is_evidentiary`` marks the two classes that may ground verification paths.
    ``is_derived`` marks retrieval artifacts that must trace to parents and are
    safe to discard and recompute.
    """

    # value = (label, rank, evidentiary, derived)
    RECEIPT = ("Receipt", 100, True, False)
    RAW_EVIDENCE = ("RawEvidence", 90, True, False)
    CAUSAL_RECORD = ("CausalRecord", 70, False, False)
    SEMANTIC_MEMORY = ("SemanticMemory", 50, False, False)
    PROCEDURAL_MEMORY = ("ProceduralMemory", 45, False, False)
    SUMMARY = ("Summary", 20, False, True)
    EMBEDDING_PROJECTION = ("EmbeddingProjection", 10, False, True)

    def __init__(self, label: str, rank: int, evidentiary: bool, derived: bool) -> None:
        self.label = label
        self.rank = rank
        self._evidentiary = evidentiary
        self._derived = derived

    @property
    def is_evidentiary(self) -> bool:
        """True only for classes that may satisfy verification paths (INV-5)."""
        return self._evidentiary

    @property
    def is_derived(self) -> bool:
        """True for disposable retrieval artifacts that must trace to parents."""
        return self._derived

    def outranks(self, other: "AuthorityClass") -> bool:
        """True if this class commands strictly more authority than ``other``."""
        return self.rank > other.rank

    def can_serve_as(self, target: "AuthorityClass") -> bool:
        """Whether a record of this class may stand in for ``target`` authority.

        A record can serve as a target class only if it carries at least the
        target's authority *and*, when the target is evidentiary, the record is
        itself evidentiary. This makes ``EmbeddingProjection`` (or any derived /
        semantic class) inadmissible as ``Receipt`` or ``RawEvidence``.
        """
        if target.is_evidentiary and not self.is_evidentiary:
            return False
        return self.rank >= target.rank

    @classmethod
    def from_label(cls, label: str) -> "AuthorityClass":
        """Resolve a class from its canonical label (e.g. ``"Receipt"``)."""
        for member in cls:
            if member.label == label:
                return member
        raise ValueError(f"unknown AuthorityClass label: {label!r}")

def _now_utc() -> str:
    return datetime.now(tz=timezone.utc).isoformat()


def make_candidate_shard_id(
    tenant_id: str,
    content: str,
    source: str = "",
    extractor_version: str = "v1",
) -> str:
    """
    Compute deterministic shard_id from candidate canonical payload.

    Uses canonical JSON (JCS-style: keys sorted, no whitespace) → SHA256.
    Same inputs always produce the same shard_id.
    Producers must NOT compute this — Cortex core is the only authority.

    Args:
        tenant_id:         Owning tenant.
        content:           Shard content string.
        source:            Source label (e.g. "conversation", "tool").
        extractor_version: Extractor version tag.

    Returns:
        Lowercase hex SHA256 digest.
    """
    canonical_payload = {
        "extractor_version": extractor_version,
        "source": source,
        "content": content,
        "tenant_id": tenant_id,
    }
    return str(sha256_hex(canonical_json(canonical_payload)))


def make_scoped_candidate_shard_id(
    tenant_id: str,
    role_id: str,
    profile_id: str,
    scope_class: str,
    content: str,
    source: str = "",
    extractor_version: str = "v1",
    handoff_to_role_id: Optional[str] = None,
) -> str:
    """Compute the scoped record identity for a served write (OPMEM-P2a, T-23).

    Same mechanism as the legacy derivation (canonical JSON → SHA256), over
    exactly this 7-key payload (canonical JSON sorts keys, so the effective
    byte order is alphabetical)::

        {content, extractor_version, profile_id, role_id, scope_class,
         source, tenant_id}

    OPMEM-P4a-T3 (identity amendment, coordinator-ratified): for the
    ``handoff`` scope class the payload gains an 8th key,
    ``handoff_to_role_id`` — distinct recipient inboxes are distinct
    authorization scopes and must hold distinct record identities (the same
    curated content handed off to two target roles is two records). Every
    other class keeps the byte-identical 7-key payload; passing
    ``handoff_to_role_id`` for a non-handoff class (or omitting it for
    ``handoff``) is a loud programming error.

    The legacy 4-key payload produces a different digest than any 7-key
    payload, so scoped ids can never collide with legacy ids. Same content
    under two scopes ⇒ two records (N-20). ``content_hash`` stays scope-free:
    no scope-free content identity is persisted anywhere.

    Only the served HTTP write path (``api.py`` ingest, which always holds a
    verified CallerScope) and the P4a curation approval path call this.
    Direct, non-served callers of the ingress model keep the legacy
    derivation, so legacy ids are unchanged.
    """
    canonical_payload = {
        "extractor_version": extractor_version,
        "source": source,
        "content": content,
        "tenant_id": tenant_id,
        "role_id": role_id,
        "profile_id": profile_id,
        "scope_class": scope_class,
    }
    if scope_class == SCOPE_CLASS_HANDOFF:
        # P4a-T3: the named recipient is part of handoff record identity.
        if not (isinstance(handoff_to_role_id, str) and handoff_to_role_id):
            raise ValueError(
                "handoff scoped identity requires handoff_to_role_id (P4a-T3)"
            )
        canonical_payload["handoff_to_role_id"] = handoff_to_role_id
    elif handoff_to_role_id is not None:
        raise ValueError(
            "handoff_to_role_id is only valid for the handoff scope class "
            f"(P4a-T3), got scope_class={scope_class!r}"
        )
    return str(sha256_hex(canonical_json(canonical_payload)))


#: URI schemes allowlisted for shards/1.1 provenance ``source_uri``

# P2a-T2(c) (R1 B F-2/A F-1): ``source_uri`` is validated on the RAW string —
# no whitespace or control characters anywhere (Python's urlsplit strips
# them, which would otherwise launder values like ``ht\tps://…`` into an
# allowlisted scheme), then a fullmatch against the allowlisted forms with a
# lowercase scheme literal (``HTTPS:`` is rejected). ``$`` is never used as
# an anchor (T-36); matching is ``re.fullmatch``.
_WHITESPACE_OR_CONTROL_RE = re.compile(r"[\s\x00-\x1f\x7f\x80-\x9f]")

    r"(?:https://[^\s]+|urn:[A-Za-z0-9][A-Za-z0-9-]{0,31}:[^\s]+)"
)

# P2a-T2(b) (R1 B F-2): ``lineage_refs`` items must fullmatch the shard-id
# syntax (no whitespace, no control characters).
_SHARD_ID_REF_RE = re.compile(r"[A-Za-z0-9_.:-]{1,128}")


def _require_clean_text(value: Optional[str], field_name: str) -> Optional[str]:
    """Reject NUL and unpaired surrogates in candidate text (P2a-T2a/T4).

    PostgreSQL text/jsonb columns cannot store NUL bytes or unpaired
    surrogates; such payloads must be refused (4xx on the served path)
    before any idempotency reservation or store access.
    """
    if value is None:
        return None
    if "\x00" in value:
        raise ValueError(f"{field_name} must not contain NUL characters")
    try:
        value.encode("utf-8")
    except UnicodeEncodeError:
        raise ValueError(
            f"{field_name} must be encodable as UTF-8 (no unpaired surrogates)"
        ) from None
    return value

        if self.decision_status is not None:
            d["decision_status"] = self.decision_status
        if self.lineage_refs is not None:
            d["lineage_refs"] = list(self.lineage_refs)
        return d

        if not self.provenance:
            return None
        provenance = self.provenance.model_dump()
        # Omit unset shards/1.1 provenance fields so shards/1 candidates
        # keep their pre-extension byte shape.
        for key in ("source_kind", "source_uri", "checkpoint_at"):
            if provenance.get(key) is None:

            raise ValueError(

                f"!= candidate.tenantId={self.candidate.tenant_id!r}"
            )

    def from_candidate(
        cls,
        candidate: MemoryShardCandidate,
        issued_by: str,

        commandId is derived deterministically from the candidate's shard_id
        so duplicate ingest commands for the same candidate are idempotent.

            candidate=candidate,

"""Deterministic ID generation.

Invariant I1a: v1 shard IDs use make_shard_id (raw concat, legacy-frozen).
Invariant I1b: all new entities use make_v2_entity_id (canonical_hash, mandatory).

WARNING — two valid ID paths exist by design:

                       exact byte-for-byte algorithm. Do not modify.

                        to canonical_hash for key-order-invariant, stable IDs.

No randomness. No timestamps in IDs.
"""

from __future__ import annotations

from typing import Any

from keon.cortex.core.canonical import canonical_hash, sha256_hex


def make_shard_id(
    tenant_id: str,
    content: str,
    source: str = "",
    extractor_version: str = "v1",
) -> str:
    """Deterministic shard_id — v1-frozen, legacy-only.

    sha256(tenant_id + ":" + source + ":" + content + ":" + extractor_version)
    Same inputs always produce the same hex digest.

    FROZEN: existing shards depend on this exact byte-for-byte algorithm.
    Do not modify this function under any circumstances.
    New entities must use make_v2_entity_id instead.
    """
    raw = f"{tenant_id}:{source}:{content}:{extractor_version}"
    return str(sha256_hex(raw.encode("utf-8")))


def make_v2_entity_id(payload: dict[str, Any]) -> str:
    """Deterministic entity ID for all new L2 entities — mandatory for new entities.

    Delegates to canonical_hash(payload): keys are sorted, output is
    key-order-invariant, and the same payload always produces the same hex digest.

    New entities introduced after PR1 must use this function.
    Do not use make_shard_id for any new entity type.

    Payload convention (callers must follow):
        Every payload passed to this function MUST include:
          - "entity_type"     (str) — e.g. "fact", "claim", "episode", "relationship"
          - "schema_version"  (str) — e.g. "1.0"
          - "tenant_id"       (str) — owning tenant

        The "entity_type" field is the type discriminator that prevents semantic
        collisions between entity classes that happen to share the same payload
        shape. Without it, a Fact and a Claim with identical remaining fields
        would produce the same ID. This function does not enforce the convention
        at runtime — enforcement belongs at the entity dataclass level.
    """
    return canonical_hash(payload)

import json
from typing import Any


def canonical_json(obj: Any) -> bytes:
    """Deterministic JSON bytes — keys sorted, no extra whitespace, ASCII-safe."""
    return json.dumps(
        obj, sort_keys=True, ensure_ascii=True, separators=(",", ":")
    ).encode("utf-8")

    """Return the lowercase hex SHA256 digest of raw bytes."""
    return hashlib.sha256(data).hexdigest()

    """SHA256 of the canonical JSON representation of obj."""
    return sha256_hex(canonical_json(obj))

        switch (MutationKind)
        {
            case ProposalMutationKind.Submission:
                if (TargetProposalId is not null)
                    throw new InvalidOperationException("Proposal submission transition cannot target another proposal.");

                if (ProposalId != RootProposalId)
                    throw new InvalidOperationException("Proposal submission transition root id must equal proposal id.");

                if (State != ProposalState.Active)
                    throw new InvalidOperationException("Proposal submission transition must remain active.");
                break;

            case ProposalMutationKind.Amendment:
                CivicMemoryContractGuards.RequireOptionalId(TargetProposalId, nameof(TargetProposalId), required: true);

                if (TargetProposalId == ProposalId)
                    throw new InvalidOperationException("Proposal amendment transition must produce a new proposal id.");

                if (State != ProposalState.Active)
                    throw new InvalidOperationException("Proposal amendment transition must remain active.");
                break;

            case ProposalMutationKind.Withdrawal:
                CivicMemoryContractGuards.RequireOptionalId(TargetProposalId, nameof(TargetProposalId), required: true);

                if (TargetProposalId != ProposalId)
                    throw new InvalidOperationException("Proposal withdrawal transition must target the withdrawn proposal id.");

                if (State != ProposalState.Withdrawn)
                    throw new InvalidOperationException("Proposal withdrawal transition must close the proposal.");
                break;
        }
    }
}
