### Findings

**F1 (fix required) — AC2 vulnerable-scan scope omits the third project.**
Locator: spec *Acceptance Criteria* #2 ("source/test project `dotnet list <project> package --include-transitive --vulnerable`").
`Keon.McpGateway.IntegrationTests.csproj` is in the slnx restore graph and transitively resolves SQLitePCLRaw native through its ProjectReference to the Gateway. As written, AC2's scan can be satisfied while the third project's resolved graph is never inspected; AC3's "vulnerable 2.1.11 is absent" similarly doesn't say *from which graphs*.
**Correction:** In AC2/AC3, enumerate all three projects (or run the transitive-vulnerable scan at solution level) and state explicitly: IntegrationTests is *scan/graph-verification scope*, not mutation scope (its file remains byte-identical to base per AC1).

**F2 (fix required) — 421/422 baseline not pinned to a named suite.**
Locator: AC4 ("`dotnet test tests/Keon.McpGateway.Tests` … 422/0/0: all 421 baseline tests preserved").
The repo contains a second test project the spec never mentions. AC4's command happens to scope correctly, but the spec's narrative baseline ("the 421-test baseline") is repo-level language checked by a project-level command. A future executor or reviewer could satisfy/dispute the count against the wrong suite, and the Integration suite — whose transitive native library *does* change — is silently unexecuted with no recorded rationale.
**Correction:** State in Constraints or AC4: "The 421-test baseline is exactly the `Keon.McpGateway.Tests` project suite (per `h1-baseline.trx`); `Keon.McpGateway.IntegrationTests` is deliberately not executed in this parcel because [it requires live services excluded by constraints / it is not part of the recorded baseline], and its non-execution is not evidence of compatibility." The Linux AC7 "same full suite" should likewise name the project.

**F3 (optional) — AC5 mutation-check venue lives only in the shaping record.**
Locator: AC5 ("a disposable mutation changing its floor to 99.0.0 fails") vs. shaping record ruling ("disposable owned copy; never edits reviewer/parcel source").
AC5 alone doesn't say *where* the mutation happens; standing-constraint Reviewer rule #11 plus the shaping ruling resolve it, but the spec is the frozen contract.
**Correction:** Append to AC5: "performed on a disposable owned copy outside the parcel worktree; parcel source is never mutated."

**F4 (optional) — AC1 wording vs. new-file addition.**
Locator: AC1 ("exactly the three allowed source paths differ from base"). The third path is a *new* file; "differ from base" is satisfied by addition, but stating "two modified + one added, no other tracked or newly tracked paths" would make the diff check mechanical and close the "extra untracked file committed" gap.
