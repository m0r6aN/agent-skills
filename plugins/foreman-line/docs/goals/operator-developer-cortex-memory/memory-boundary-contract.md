# OPMEM-P0 — Memory boundary contract (AC3 + AC4 + AC7)

**Parcel:** OPMEM-P0 · **Evidence base:** `source-baseline.md`, `canon-authority-map.md`
**Status:** frozen contract proposal for independent review. It resolves the proposed-vs-actual seams found at the pinned revisions. Numeric limits that require owner approval are collected in §7 and `open-decisions.md`; they are approval items, not silently chosen values.

## 1. Frozen topology (D3/D4/D5)

```text
Pi lifecycle extension / memory tools            [P7 — missing today]
  -> local adapter container (loopback/stdio)    [P6 — bridge shell exists, outbox missing]
  -> Azure MCP Gateway                           [ingress authority: identity, scope, entitlement, receipts]
  -> Azure Cortex                                [memory semantics: shards, lineage, evidence, gravity, recall, verification]
  -> Neon Postgres                               [Cortex-owned durable storage]
```

Non-negotiables carried from the ratified plan and confirmed against source:

- Gateway is the **sole** agent-facing service ingress. Direct client→adapter use is a dev profile only (bridge `README.md` "Canonical topology").
- Neither Pi nor the adapter receives database credentials or calls Cortex directly. The bridge contains no storage, gravity, proof, signing, or policy implementation (bridge `README.md`; `docs/CORTEX_PORT_CONTRACT.md` status line: "integration proposal, not locked Cortex canon").
- Cortex owns memory semantics/verification/lineage/gravity/durable storage. Gateway owns trusted tenant/profile/role binding and governance. The adapter owns delivery state only.

### 2.3 Frozen boundary attributes per seam

**Auth.** Cortex trusts exactly one caller: the Gateway, via `X-Keon-Cortex-Secret` (constant-time compare, `api.py:164-175`). Every Cortex route additionally requires `X-Tenant-Id` and `X-Actor-Id` (`api.py:138-145`) — at the Cortex boundary these arrive only from the Gateway's `CortexClient` (`AddTenantHeaders`, `CortexClient.cs:250-254`), which forwards whatever tenant/actor the Gateway caller context carries. **That caller context is agent-influenceable at pin:** `McpCallerContextResolver.cs:49-59` resolves tenant/actor with precedence **client request headers `X-Keon-Tenant-Id`/`X-Keon-Actor-Id` → configured defaults (`McpOptions.DefaultTenantId`/`DefaultActorId`) → token claims**. JWT mode is safe because `JwtValidator.cs:53-62` binds claims↔request and mismatches fail closed (`MCP_TENANT_MISMATCH`), but API-key/machine-credential mode binds **only the tenant** (`ApiKeyValidator.cs:88-92`) and copies the client-supplied `actorId` unverified into the principal (`ApiKeyValidator.cs:107-108`, `new Claim("actor_id", actorId)`); a forged actor then flows into Cortex `X-Actor-Id`, `Provenance.agent_id`, and `_request_hash` (`api.py:260-267`). **Frozen contract (OD-5 as amended by R0 F-1):** client headers may never override authenticated claims; API-key/machine-credential principals carry an enrollment-bound actor/role, never a client-asserted one (§4.1 rule 6; enforcement owned by P1a; negative fixtures N-14/N-15). Gateway authenticates callers with JWT (`JwtValidator`, scopes such as `keon:mcp:invoke`, `keon:cortex:write`, `keon:mcp:list`) or API key (`ApiKeyValidator`), and evaluates entitlements (`IEntitlementEvaluator`, `PackageTier.Cortex`). The adapter authenticates to Gateway per the Gateway-supported scheme (D6); today the bridge carries startup-fixed identity only (§4.2).

**Trusted scope carriage (T-1, 2026-10-12 ruling).** On every Cortex call the Gateway additionally emits `X-Keon-Role-Id`, `X-Keon-Role-Generation`, `X-Keon-Profile-Id`, `X-Keon-Grant-Scopes` (canonical, sorted, comma-joined scope ids), `X-Keon-Session-Id`, and `X-Keon-Task-Id` (the §3 logical task identity, T-29), taken from the verified §4.1 binding — never from client input. Cortex trusts these headers **only** on requests authenticated by the existing Gateway secret (`_authorize_gateway`, `api.py:164-175`) and fails closed when role/profile are absent on memory routes. Emission owner: P1a (`Backends/CortexClient.cs`); acceptance + served-path enforcement owner: P1b (`api.py`; scope persistence in `providers/postgres/schema.py`; same-tenant cross-role and operator→live HTTP tests in `tests/test_scope_http.py`). `X-Keon-Task-Id` is advisory context, never an authorization input; P2 persists it on every recall/access event (T-29).

**Secret custody and reachability (T-19, OD-20).** The trust root for all carriage above is `X-Keon-Cortex-Secret`; the frozen requirement: Cortex memory routes must be **network-reachable only from the Gateway**; the secret is **per-environment**, held only by Gateway and Cortex, and **rotatable without downtime** (dual-secret acceptance window); compromise ⇒ rotate + re-audit. Implementation owner: **P8**. Until P8, `opmem/integration` code is not deployed (merge boundary), so OPMEM adds no live exposure.

**Schema.** Cortex ingest body is `MemoryShardCandidate` (canonical fields: `content`, `source`, `memory_type`, `memory_mode`, `subject_keys`, `belief_score`, `extractor_version`); shard identity is deterministic (`compute_shard_id`), request identity for idempotency is `_request_hash` = sha256 over canonical JSON of the candidate plus `actorId` (`api.py:260-267`). Gateway tools accept a JSON subset (`content` required; `source`, `memory_type`, `memory_mode`, `subject_keys`, `belief_score` required for write) and return contract objects (`shard_id`, `decision_id`, `store_ack_id`, `correlation_id`). **Additive wire version `shards/1.1`** (T-12, OD-4 refinement — not a frozen-canon change): `memory_type` gains `observation`, `decision`, `artifact_link` (the pin validator `ingress/models.py:153-158` accepts only `claim|belief|lesson|fact|story`, so the §2.2 mapping is unroutable until this lands); the candidate gains optional structured `provenance` (source kind/uri/checkpoint time — extending the existing optional `provenance`/`CandidateProvenance`, `ingress/models.py:82-96`, `:136`), `decision_status`, and `lineage_refs`. `shards/1` payloads remain valid. Owner: P2 (`ingress/models.py`, `providers/postgres/schema.py`, plus the durable model `core/models.py` and `providers/postgres/document_store.py` per T-22); Gateway input schema owner: P5a. Persisted record-scope fields (`role_id`, `profile_id`, `scope_class`) are P1b schema work (T-1) — sequential handoff on `schema.py` (T-2). Round-trip fixtures in P2/P5a prove these fields survive authoritative storage. **Record vs content identity (T-23).** For `shards/1.1` writes, **record identity** = hash(tenant, `role_id`, `profile_id`, `scope_class`, content, source, extractor version); **content identity** (`content_hash`) stays scope-free and is used for display/dedupe hints only — it never merges records across scopes. Legacy `shards/1` ids are unchanged (fixture N-20).

**Response.** Cortex data routes return an envelope `{"success": true, "data": …}` (`api.py:464`, `:513`, `:537`, `:556`, `:571`, `:608`, `:658`); the exception is `GET /health`, which returns `{"ok", "storage"}` (`api.py:401-406`) and must not be envelope-parsed. The adapter must echo and verify `tenant_id`/`project_id` scope (bridge `_validated_response`) and fail closed on foreign-tenant/mixed rows. `CortexStoreAck(ShardId, StoreAckId, ValueHash)` is the write acknowledgement; search returns `CortexShardSummary` rows with `RelevanceScore`, `LineageHash`, `CreatedAt`, `Status`. **Backend ownership preservation (T-8):** Gateway projections of Cortex rows carry the row's **backend** `tenant_id`/scope fields (`CortexShardSummary` gains them — `CortexClient.cs:44-55`); handlers reject any row whose ownership is missing or ≠ caller scope with a fail-closed **error** (never a silent drop) and never synthesize ownership from the caller — the pin behavior at `CortexMemorySearchHandler.cs:85` (writing `tenant_id = context.Request.TenantId` onto every row) is a defect P5a fixes; N-10 executes through the real client→handler→adapter path.

**Readiness.** Cortex `GET /health` returns only `{"ok", "storage"}` at pin (`api.py:401-406`) — the shards wire carries **no** `schema_version`/protocol field anywhere (tool names carry `.v1`; there is no version header). Adapter `GET /health/live` + `GET /health/ready` return `503` until a *compatible ready* backend exists (bridge `server.py:172-175`, `ADVERSARIAL_GATE.md`). Readiness truth: `{"status":"ready","schema_version":"…"}` requires authoritative storage + schema compatibility + required signing/proof dependencies (port contract §Operations) — the adapter must not report ready on a liveness-only backend. **The schema-version signal does not exist on the wire today; P2 owns adding it** (Cortex `/health` gains a `schema_version`/protocol field — `api.py` is in P2's Allowed Files; the adapter fails closed on mismatch per the Version row; ruling OD-17 in `open-decisions.md` §B). This keeps the S-10 downgrade-refusal test implementable. The adapter learns the signal through **`keon.cortex.capabilities.v1`** (T-13) — the Gateway tool returning Cortex `/health` `{ok, storage, schema_version, protocol}` plus the Gateway version over the adapter's sole ingress (owner P5a: `Tools/Cortex/CortexCapabilitiesHandler.cs`, `CortexClient.cs`); the adapter validates protocol/schema against it and fails closed — an incompatible Cortex behind a healthy Gateway ⇒ adapter **not-ready**.

**Version.** Tool names carry `.v1`; the wire carries no version header and no `schema_version` field today (P2 adds it to `/health` — see Readiness). **Contract:** the shards wire is protocol `shards/1` (plus the additive `shards/1.1` semantic extension — see Schema, T-12); adapters MUST refuse protocol downgrade (a backend advertising a different schema_version than pinned → fail closed, `degradation: null` with explicit error). A future `shards/2` is additive (new fields), never silently re-typed; removal/retyping requires a version bump + owner amendment.

**Error.** Cortex errors are HTTP status + detail; Gateway maps to `CortexClientException(retryable)`; the adapter maps to sanitized MCP `ToolError` JSON with `indeterminate=true` on timeout/unavailable (`server.py:_error`, VERIFICATION.md "unavailable-backend call"). **Frozen rule:** a timeout on a write or recall is an **indeterminate** result, never success and never a fabricated duplicate; reconciliation is by idempotency key (§6).

**Idempotency.** The `X-Idempotency-Key` header is **optional** (wire alias `X-Idempotency-Key`, `api.py:419`; T-4): absent or blank, the key falls back to `shard_id` (`api.py:436-440`, within the reservation path `api.py:418-449`). The mandatory ingest gate is `X-Decision-Receipt-Id` — requests without it are refused 403 (`api.py:425-433`). Reuse of a key with a different request hash is refused ("idempotency key was reused with a conflicting request", `api.py:320`); the reservation is durable in `keon_cortex.api_idempotency` keyed `(tenant_id, idempotency_key)` with `UNIQUE (tenant_id, shard_id)`. `status: duplicate` semantics for an identical retry are part of the port contract; exact response bytes must be pinned by P2 tests (OD-6).

**End-to-end retry identity (T-11).** The adapter mints a durable `operation_id` per logical operation (P6 outbox identity — §6 Outbox row), carried as `X-Keon-Operation-Id`. **Writes:** the Gateway binds `operation_id` → original decision receipt + Cortex ack in a durable operation ledger (`Spine/OperationLedger.cs`, P5a) and reuses them on retry — no fresh Runtime decide for a known operation; flush-time reauthorization still applies to *new* operations and to operations whose original grant was revoked (revocation ⇒ fail, not reuse). **Recalls:** Cortex binds `operation_id` → original selection + `recall_event_id` and returns the same selection on retry (P2). Operation ledgers (the Gateway write ledger and the Cortex recall binding) key on `(tenant, actor, role_id, profile_id, operation_id)` and store a **request fingerprint** that includes the original authorization context; the same `operation_id` under a different scope or a changed fingerprint ⇒ **refuse (conflict)**; returning a cached ack/selection **re-checks current authorization** first (T-23; fixture N-21).

### 2.4 The recall seam is CLOSED until P2 (resolution C-5)

The deployed `POST /v1/shards/search` is term-overlap relevance (`len(terms ∩ content)/len(terms)` over `list_by_tenant(limit=1000)`, `api.py:515-543`). It does **not** append a Recall spine event, does not compute gravity, does not verify content hashes, and returns no `recall_event_id`/`gravity_score`/`verification_meta`. The bridge's mandatory recall response (port contract) and the two-plane `RecallService` (`spine/recall_service.py`) are therefore **not implementable/not wired** respectively.

Contract consequences frozen now:

1. No OPMEM component may claim "gravitational recall" or "verified recall" over the deployed path until P2 lands the recall-event append + `RecallService` join + content-hash fail-closed behaviour on the served path (INV-2/INV-1).
2. Search results must be labeled `relevance_score` (term overlap), never `gravity_score`, and carry `verified: false` / `verification_meta: unavailable` until then.
3. `recall.v1` tool exposure stays behind the P7 feature flag until its response contract is satisfiable end-to-end; interim, adapters expose `search` semantics only.
4. Recall accounting (a durable recall event per genuinely new delivered recall) begins at P2/P3; no retroactive event fabrication.

Receipt discipline (INV-5): receipts are typed by **verified semantics, not prefix** (T-10): a **governance decision receipt** records the Runtime decide (`decision.ReceiptId`, `CortexMemoryWriteHandler.cs:108`); a **tool-terminal outcome receipt** records the tool invocation's terminal status — which may be `terminal_status=denied` with a **null execution receipt** (`Spine/InvokeTerminalWriter.cs`, `Spine/IngressSpine.cs` `OutcomeFactory`); an **action-execution receipt** records that an action actually ran. A denied action preserves its governance + terminal receipts and has **no action-execution receipt and no observed action outcome**. `rcpt_*` ids are emitted through Gateway→Runtime (`CortexMemoryWriteHandler.cs:107-120` emits directive/intent/decision/outcome receipts). `delib_*`, `inherit_`, narrative, and `BranchRecord` objects are **cognitive** records; receipt verification must never consult them and they must never satisfy a verification path. The Cortex-side `receipt_ref.integrity_hash` is a local anchor of an opaque Gateway id ("without claiming remote verification", `api.py:176-181`) and must not be described as remote proof.

## 4. Identity / profile / ancestry seam (AC4)

### 4.1 Authoritative role assignment — GAP, contract now, implementation in P1

No inspected surface has a role concept: Gateway `Auth/` contains only `JwtValidator`/`ApiKeyValidator`; requests carry `tenant_id`/`actor_id` (+ `correlation_id`); Cortex carries `X-Tenant-Id`/`X-Actor-Id`; the bridge carries `KEON_TENANT_ID/ACTOR_ID/AGENT_INSTANCE_ID/PLATFORM`. OPMEM requires long-lived **role** identity (D9). The contract:

1. **Role is trusted dispatch/enrollment context, never an MCP argument.** A role claim must be bound by the Gateway from (a) Foreman-dispatch context for dispatched agents, or (b) interactive enrollment for human-started Pi sessions. Any `role` field arriving in a tool argument is rejected before backend calls (negative test N-1).
2. **Foreman-dispatched sessions:** the dispatch record (issuer-validated) supplies role + generation + task scope; Gateway validates the issuer seam and mints a session-scoped binding. Missing role ⇒ **fail closed**, never default coordinator privileges (negative test N-2).
3. **Interactive Pi sessions:** explicit non-Foreman enrollment (operator-approved) with expiry and revocation; headless mode must have a pre-provisioned machine credential or refuse memory writes.
4. **Role ≠ generation ≠ agent instance ≠ session ≠ model.** All five identifiers are distinct fields everywhere (D1/plan §4). A restarted agent with the same role keeps role continuity **without** inheriting raw ancestry (see §4.3).
5. **Machine credentials** (D6): separate, revocable, shared across sessions on that machine, but they authorize *machine* trust only — not every role. Revocation/expiry must fail closed at flush time, not only at enqueue.
6. **Verified actor/role binding** (OD-5 as amended by R0 F-1): client-supplied transport headers (`X-Keon-Tenant-Id`/`X-Keon-Actor-Id`) or tool arguments may **never** override authenticated claims. Under JWT the Gateway binds claims↔request and mismatches fail closed (`JwtValidator.cs:53-62`, `MCP_TENANT_MISMATCH`); under API-key/machine credentials the actor/role is the enrollment-bound one from the credential record — the client-asserted `actorId` is never copied into the principal (the pin behavior at `ApiKeyValidator.cs:107-108` and the header precedence at `McpCallerContextResolver.cs:49-59` are defects P1a fixes). Transport-header identity spoofing and machine-credential actor spoofing fail closed before any Cortex call (negative tests N-14, N-15).

### 4.2 Portable tenant / repository identity

- Tenant identity is stable across the three machines; it is **not** derived from MAC/IP, checkout path, model, or agent lifetime (D1). Server-side `require_tenant` remains the hard gate.
- Repository identity must be canonical (portable across remotes/forks/worktrees/WSL paths/machines). Contract: repository identity = the **canonical remote identity** (host + namespace + repo) recorded at capture, with the raw absolute path retained only as a provenance hint. A bare local path is never a repository id (negative test N-3: two machines' paths for the same repo must resolve to one identity; one path hosting two repos must not merge them).
- `subject_keys`/`project` scope carried on writes is server-validated against the caller's grants; **local configuration may narrow but never widen** server grants (D2).

### 4.3 Private ancestry and shared exceptions

- Raw ancestral scope of a role is private to that role (D9). Exact-ID retrieval (`get_memory.v1`), lineage traversal (`lineage.get.v1`), feedback, and curation are all subject to the same server-side scope check **before** candidate generation and again at the response boundary (plan §3).
- Cross-role visibility is limited to: explicit handoff artifacts, owner-approved shared developer preferences, and approved general lessons. **Opaque references do not leak ancestry** (negative test N-4: possessing a `memory_id`/`lineage` pointer from another role must fail, not return metadata — exact-ID cases execute through `memory.get.v1`, T-24).
- Derived summaries (distillation) carry `source_refs` lineage and epistemic status; a derived record gains **no** factual or authorization authority from being summarized (anti-laundering, inheritance validator rule 5). Active/primary inheritance requires the approval receipt (rule 3).
- Live application/family profiles are administrative, default-deny grants outside configured scope (D16): sharing a Keon service dependency or repository never shares application memory (negative test N-5).
- **Record scope and legacy rows (T-1).** Every stored record carries persisted scope fields (`role_id`, `profile_id`, `scope_class`) written at ingest from the trusted carriage headers (§2.3 Auth). Scope checks evaluate the caller's grant scopes against the record's scope **before** candidate generation and again at the response boundary. Legacy rows written before scope fields existed are readable only by the operator profile's own role-less "legacy" scope and are **never** visible to live profiles (fail closed).

### 4.4 Negative fixture set (minimum; full list in `event-and-fixture-contract.md` §7)
