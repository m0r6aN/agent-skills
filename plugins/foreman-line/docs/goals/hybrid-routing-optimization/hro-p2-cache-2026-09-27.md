# HRO-P2 delivery record — deterministic cache reuse (2026-09-27)

**Parcel:** HRO-P2 (charter row: "Add deterministic cache reuse to the existing evaluator;
demonstrate cold/warm parity, invalidation, and revalidation of all dynamic gates; prove
unavailable/corrupt cache cannot weaken authorization").
**Authority:** coordinator implementation 2026-09-27 under owner blanket authority (2026-09-26).
**Surfaces:** `dispatch/src/routing-cache.ts` (new), `dispatch/src/routing-eval/index.ts` (wired),
`dispatch/tests/routing-cache.test.ts` (new). `routing-policy/**` untouched.

## What shipped

- **Indexed exact decision cache** (charter D4): canonical key = sha256 over schema version,
  policy content digest, task class, data classification — every input that changes eligibility
  or ranking in the current evaluator. Key separation tested (5 distinct keys).
- **Revalidation, never trust (D1/D4):** input gates (class/classification) run identically on
  warm and cold paths before any lookup; every recall re-checks schema version, policy digest,
  record shape (ajv, boundary-validated), a content seal, and TTL. Warm hits skip only
  parse+validate+walk under a digest-matched record — the decision can never outlive or
  contradict the policy bytes it was made under.
- **Invalidation:** policy byte changes diverge the key (plain miss, never a stale hit);
  TTL expiry is a typed miss; `invalidateAll()` for explicit cutovers. The `policy-changed`
  diagnostic covers digest-mismatched records at a matching key (mixed store content).
- **Corruption cannot weaken authorization:** unparseable store documents are quarantined
  (`.corrupt`) and treated as empty; field-level corruption breaks the content seal and is a
  typed `corrupt-record` miss; the evaluator then re-derives the TRUE decision on the cold
  path (test flips `resolvedModelId` and asserts the honest model is returned). Stated limit:
  the seal is a corruption detector, not a secret-keyed MAC — a hostile store with write
  access can re-seal forgeries; no local mechanism prevents that.
- **Store semantics (D4):** bounded exact queries, map-keyed uniqueness, atomic tmp+rename
  upserts, explicit lockfile lifecycle (`CacheStoreConflictError` on concurrent open),
  max-entries oldest-first eviction, open/close lifecycle. Storage follows the plugin's JSON
  persistence convention; `node:sqlite` is still experimental on the pinned runtime (verified
  24.7.0) and no new dependency was added (D6).
- **Cache failure = same cold path, never weaker:** store throws become typed diagnostics;
  `recall` never throws; tests prove unavailable-store parity.

## Honest boundaries (recorded, not claimed)

- **Dynamic budget/availability/independence gates** (D4) do not exist in the current
  `RoutingInput` contract (class + classification + workflowId). The revalidation seam is
  explicit (pre-lookup input gates + `recall`'s gate chain); when richer dynamic inputs land
  (RCM currency preflight / HRO-P4 budgets), they extend the key or the revalidation chain.
  No budget fields were invented.
- **Duplicate-settlement protection** (acceptance bullet) is the receipt contract's own
  one-receipt-per-workflowId behavior plus the store's uniqueness; full event accounting is
  HRO-P3 (telemetry) scope.
- Cache location is caller-supplied (explicit store path); no repo layout invented.
