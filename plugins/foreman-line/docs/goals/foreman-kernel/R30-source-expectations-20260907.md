Classification shorthand in the tables:

- **IJ**: `independent-review-human-judgment`. A binding planning, scope, verification, reporting or acceptance obligation. It is not proof of mechanical enforcement.
- **PR**: `pre-action-refusal`. Source prescribes refusing a governed action under a named condition. A future kernel/adapter mechanism is still unimplemented/unproven here.
- **PD**: `post-action-detection`. Source requires measurement/recording after an observation, not pre-action blocking merely because a target was missed.
- **NP**: `narrative-provenance`. Historical fact, rationale, source reference or corroborating restatement; cannot independently mint authority.
- **V**: declared volatile operational content, excluded through the existing region extent, not a new rule classification.

Assurance for all newly published normative expectations below is **human-ratified source intent only**. If represented by the existing assurance enum, distinguish `human-ratified` provenance from any future `structural`, `detected`, `mediated`, or `independently-verified` implementation claim. **M** marks compound treatment: separate the listed semantic components, or explicitly map each component through a reviewed compound rule. ## Supplemental assurance exception recommendation

The inspected baseline contains a concrete mismatch between source intent and default rule shapes: `src/generate.ts` function `ruleShape` assigns `independently-verified` to every `independent-review-human-judgment` rule, `detected` to post-action/CI rules, and `structural` to ordinary pre-action rules. `src/validate.ts` `CLASSIFICATION_CONTRACT` and the pre-action shape branch enforce those pairings. Those defaults must not make the R30 source-intent publication claim runtime or review evidence it does not have.

Recommended exact envelope: a finite, reviewed **R30 source-intent assurance exception map** maintained as trusted package code, not supplied by the registry document. Each entry binds one concrete rule and its independently reviewed expected shape. The exception permits **only** substitution of `human-ratified` assurance for the ordinary class-derived assurance when the complete entry matches. Unknown identities and all nonmatching shapes continue through the original validator checks and refuse invalid changes. There is no global `human-ratified` exemption and no source-wide, prefix, paragraph-count or classification-wide exemption.

Each exception entry must bind all of the following explicitly:

1. Exact `ruleId`, `authoritySubject` and `authorityClaim`, including any compound suffix. Entries are one per expected rule, not one broad allowance for a source unit.
2. Exact existing `sourceId`, item ID, locator kind/anchor and locator digest, plus normalized source value digest. The authority-basis reference and all source references must be the expected complete set. No matching on just a source path, heading prefix or free-form normalized substring.
3. Exact classification, decision, refusal code, enforcement owner, authority scope/applicability axes, severity, paired-rule IDs, retirement state and retirement-evidence shape. Preserve every non-assurance field under the already reviewed rule contract. Do not opportunistically change decision/owner just to gain entry to the exception path.
4. The single permitted assurance value `human-ratified`; the declaration means the source requirement has human ratification, not that the mechanism is implemented, the reviewer acted, or a request's gate is satisfied.
5. A source-backed reason linking the entry to its C/L/U expectation components and the R30 adoption/amendment. This traceability text is explanatory; it cannot substitute for identity/location/value/shape comparison.

The builder must propose the finite literal entries from the source expectation set and independently review their source/shape mappings. Do not populate expected values by accepting whatever the candidate document generates at runtime. A canonical expected-shape digest may compact the complete comparison, but it must be an independently approved literal over a documented closed field set, not a digest read from the same untrusted document. Ordinary rule binding, source sweep, manifest binding, exact eighteen-source enforcement, chain validation and retired-rule evidence checks remain mandatory after an exception match. An exception is not an early success return from validation.

Keep the existing global class contract unchanged for every other rule. Preserve loaded-profile mediated assurance, established Gate2 ALLOW rules, protected-operation principals/booleans/evidence, and the prohibition on runtime grant minting. Do not expand the exception map to all old rules merely because their assurance wording may also deserve review; that is outside this narrow source-adoption fix. For an already-published rule such as D21, name the exact affected rule/component and preserve its non-assurance semantics and migration history before changing its assurance.

Required later verification should demonstrate both sides of this boundary: an exact reviewed R30 entry with `human-ratified` is admitted; substitutions in identity, location, value, class, decision, owner, applicability or other bound shape fail; unrelated rules do not acquire the exception by copying the assurance string; copying an approved entry onto a different rule fails; and rule/source/manifest mutations still fail after passing the exception selector. Preserve ordinary non-R30 negative controls. These are requirements for the builder's future verification, not test results from this docs-only supplement.

If a proposed rule needs a different owner/decision as well as different assurance, this recommendation alone does not authorize it. Return the concrete source clause and exact proposed shape for separate scoped ruling, without changing global classification semantics. In particular, neither U02/U03 nor L01/L02 creates a new ALLOW entry through this assurance mechanism.
