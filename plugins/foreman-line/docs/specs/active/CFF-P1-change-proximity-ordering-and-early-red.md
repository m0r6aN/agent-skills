# CFF-P1 — Change-proximity ordering and early-red signal

## Intent

Within each shard, order the already-assigned packages' checks by proximity to
the diff (consuming the D7 measured read graph fail-safe, over-approximation
only) with a deterministic tie-break, so a swept failure's signal exists
sooner without touching which packages a shard owns or how many shards exist.
Add the D8 early-red surface (signal-only: shard-early-exit at the first
non-waived failure, plus sanitized `::error`/`::warning` annotations) so a red
is visible in the job log before the slowest shard finishes, without ever
deciding the verdict early. Carry the two named `D10` bookkeeping duties this
goal routed here: the 30-package `COST_TABLE` re-pin that restores the
ratified cost-aware shard assignment (loudly, with coverage surfaced before
and after), and the Stage-F disposition record for the four dead
`WAIVED_EXCLUSIONS` entries CFF-P0 found. Own the D11 shared diff seam
(`ci-reuse.mjs`, `GITHUB_EVENT_PATH` base selection, fail-closed on
absent/all-zeros) so no second differ is ever built. None of this may change
*what* a package's check output means to the waiver machinery (D3) or *when*
the all-artifact verdict is decided (D6/D8's invariant).

## Acceptance Criteria

### AC1 — Change-proximity ordering within a shard (charter idea; D3; D7 fail-safe)

- **What "proximity" means, pinned to D7's actual shape.** D7 defines a
  **measured read-graph affection relation**: for a given package, the set of
  paths its checks are proven to read (imports and non-import couplings).
  It is a per-package relation, not a weighted or multi-hop distance graph —
  nothing in the ratified D7 text defines a notion of "how many hops away."
  Proximity for ordering purposes is therefore the only property D7 actually
  supports: **binary, per package, per run** — a package is *proximate* to
  the current diff if its read-graph entry (including named R15 variance
  edges, which always count toward affection, §AC2) intersects the current
  changed-paths set (§AC6); otherwise it is *not proximate*. Any future
  multi-hop or weighted notion is out of scope here — it would require a D7
  amendment this parcel does not request.
- **The ordering rule.** Within a shard's phase-2 iteration (the `mine`
  loop in `runShard`), proximate packages run before non-proximate packages.
  **Deterministic tie-break:** within each of the two groups, packages run
  in ascending code-point name order — the same order `discoverPackages`
  already returns and `assignShards`' round-robin branch already preserves,
  so a build where proximity computation is unavailable (AC2) degrades
  byte-identically to today's order, not to an arbitrary one.
- **Ordering never excludes.** Every package assigned to the shard
  (`assignShards(discovered, shardCount)[shardIndex]`, unchanged by this
  parcel) still runs every one of its checks exactly as before, in exactly
  the same shard; only the iteration order within phase 2 changes. The D7
  pin is consumed in zero places as a filter — grep-verifiable: no new code
  path removes a name from `mine` based on the pin.
- **D3 preserved by construction.** Ordering changes *when* a `(package,
  check)` pair's `invoke()` call happens, never changes the call itself, its
  arguments, its `cwd`, or how its `output` string is assembled
  (`${stdout}${stderr}`, one call per pair, §AC7). No batching, no
  concurrent execution of two packages' checks is introduced (interleaving
  is a hard stop).

### AC2 — D7 pin consumption contract, pinned without assuming contents

Because `read-graph.json` is CFF-P0's in-flight artifact (possibly absent at
this parcel's build or run time), the consumption code is built against the
**contract**, never a committed fixture of real content:

- **Location and schema gate.** The pin is read, read-only, from
  `plugins/foreman-line/docs/goals/ci-fail-fast/read-graph/read-graph.json`
  if and only if that file exists. A present file whose top-level `schema`
  field is not exactly the string `foreman-line-ci/read-graph@1`, or that
  fails to parse as JSON, or whose per-package entries are not an object
  structurally capable of expressing only **positive** coverage (no
  `excludes`/`not-affected` field of any name or shape — confirmed by
  CFF-P0's own AC5.6 property: "schema can express positive coverage only"),
  is a **malformed pin**.
- **R15 variance edges.** Per D7/R15, an edge proven under only one
  environment is a *named variance edge*: it always counts toward a
  package's affection (always-affect), and its absence from a clean pass
  never excludes the package (never-exclude). This parcel's proximity
  computation treats a variance-marked edge identically to an ordinary edge
  for the "is this package proximate" test — it only ever adds a package to
  the proximate group, never removes one.
- **Fail-closed, per D6, by reference.** A **missing file**, a **malformed
  pin**, or any error raised while computing the proximate set for the
  current diff (§AC6) disables proximity computation for that run: every
  package in the shard falls back to the single non-proximate group,
  ascending-name order — i.e. **today's order**, named in D6 by reference to
  `assignShards`/`runShard` as ratified, never a snapshot. This is NOT a
  shard-membership fallback (AC2 never touches `assignShards`) — it is
  scoped to ordering alone.
- **Criticality grading matches D7.** This parcel is the fail-safe consumer
  named in D7: a wrong proximity computation can only **mis-order** a
  shard's checks (latency effect), never skip one (coverage effect) — the
  "ordering never excludes" property in AC1 is the structural proof.

### AC5 — D8 named early-red signal surface

- **(a) Shard-early-exit.** `runShard`'s phase-2 loop stops iterating `mine`
  at the first `(package, check)` whose result is a **non-waived failure**
  (`records.get(name).checks[check]` set to `fail` or `error` — i.e. the
  `evaluation.record === null` branch, which includes any `invoke` result
  with `kind !== 'exit'`: every failure reaches `evaluateWaiver` (:918) and
  non-exit kinds are rejected at its kind-gate (:701) with `record: null` —
  path description corrected at coordinator lint 2026-10-08 erratum E2). Every package/check
  pair not yet reached keeps its pre-populated `skipped` status in `records`
  (unchanged initialization). The function still returns its `artifact`
  (built from `records`, exactly as today) and a non-zero `exitCode`; the
  CLI's `shard` mode still writes that artifact to disk before returning
  (unchanged — `runCli`'s `shard` branch already writes before checking
  `result.exitCode`, confirmed at the CLI layer). The workflow's existing
  `if: ${{ !cancelled() }}` upload step (unchanged, no workflow edit needed)
  therefore still uploads the partial artifact.
- **`reconcile` fails closed on the partial state, unmodified logic.**
  `EXPECTED_SKIPS` is empty (confirmed `:623`); any `skipped` check in the
  uploaded artifact already produces `unexpected-skip` (AC3 rule #6,
  `reconcile` :1077-1082, unchanged by this parcel) and any check entry a
  shard never reaches but a *different* artifact's logic expects produces
  `missing-checks` where applicable — this parcel adds no new reconcile
  branch; it relies on the existing nine-way failure enumeration already
  covering a partial artifact's shape, which the harness tests prove
  (AC8).
- **(b) Sanitized annotations at failure time.** At the exact point a check
  is recorded `fail` or `error` (never on `waived` passes, never on `pass`),
  the runner emits one GitHub Actions `::error` workflow command to stdout;
  at the exact point a check is recorded `waived`, it emits one `::warning`
  command. Both commands' interpolated fields (`file=<package>`,
  `title=<check>`, and the message body) are built **only** from fixed-shape
  data already available without re-reading captured output —package name,
  check name, and the evaluation's `layer` code (for waived/rejected cases,
  already named by `evaluation.layer`) — each run through `sanitizeField`
  before interpolation (standing constraint #4/SC31; the annotation's own
  literal `::error`/`::warning`/`file=`/`title=` tokens are emitted by this
  parcel's code, never derived from untrusted text, so they cannot be
  forged by a package name or check output containing `::`). **Raw captured
  `output` text is never placed in an annotation field** — the existing
  `echoCheck`/`sanitizeOutput` path remains the only place captured text
  reaches the log, unchanged.
- **Structural prohibitions, verified absent.** No change touches: sibling
  shard cancellation (no `cancel-in-progress`, no cross-job signal added);
  `needs`/job scheduling (`.github/workflows/foreman-line-ci.yml` is not in
  `Allowed Files`); any early-green path (the early exit only ever sets
  `exitCode: 1`, never `0`, and never writes a `pass` status for an unreached
  check); any check-run/status emitter (`checks: write`/`statuses: write`
  are not requested or used — `::error`/`::warning` are log-level workflow
  commands, not the Checks API). **Invariant, tested:** the required `test`
  context still reaches a terminal state on every run exactly as today — the
  surface changes when a red becomes *visible*, never when the verdict is
  *decided* (`verdict()` :1150 is untouched by this parcel).

### AC6 — D11 shared diff seam owned in `ci-reuse.mjs`

- **One new export, one source.** `scripts/ci-reuse.mjs` gains exactly one
  new exported function providing the changed-paths set for a run, built
  **only** from `parseNameStatusZ` (`:416`) and `classifyPath`/`READER_SET`
  (`:175`/`:129`) already in that file — neither reimplemented nor
  duplicated. No other file in this parcel computes a diff; `runShard`/AC1's
  proximity computation calls this one export, never `git diff` directly.
- **Base selection, pinned exactly as D11 states.** Base SHA resolution
  reads the event payload at `GITHUB_EVENT_PATH` (seam confirmed unchanged
  at `:1086`): on `pull_request`, the PR's base SHA; on `push`, `event.before`.
  **Absent `GITHUB_EVENT_PATH`, an unparseable payload, or an all-zeros /
  non-hex40 base SHA is a fail-closed condition** — the export returns a
  signal (e.g. `paths: null`) that AC1/AC2's proximity computation treats
  identically to "pin malformed" (falls back to ascending-name order, never
  throws, never treats an unresolved base as "no changes").
- **No runner-local differ, no gate-output dependency.** The export invokes
  `git` directly (as `ci-reuse.mjs`'s existing `gitBytes`-style seam already

  second tool and never reads a gate job's output (which rule 0, `:746`,

  break on push, the exact failure D11 forecloses).
- **Classification reuse, not reinvention.** Each changed path is classified

  proximity test, so a path D2's classification already proves
  `ordinary_documentation` for contributes nothing to proximity the same way
  it contributes nothing to CI-P1's reuse decision — no second
  classification engine, no divergent notion of "this path matters."

### AC7 — D3 conformance test against the CFF-P0 contract

A dedicated test (or test group) in `scripts/foreman-line-ci.test.mjs` proves
every point of `cff-p0-waiver-input-contract.md` §3 holds under reordered
execution, by construction of the fixture (mutate-the-fixture discipline,

   is invisible to the per-package capture.
2. **Same stream concatenation.** No test introduces or permits a
   multi-package concatenated buffer; each `invoke()` call's `output` remains
   `${stdout}${stderr}` for exactly one `(package, check)` pair.
3. **Same granularity.** No fixture batches two checks into one
   `evaluateWaiver` call; the one-call-per-pair shape from AC1 is asserted
   directly.
4. **Same waiver parsing.** `failingTestNames`/`sumFailTotals`/`countOccurrences`
   and the nine-layer `evaluateWaiver` order are exercised, unmodified, with a
   waived fixture and a rejected fixture, under both an ordinary and a
   proximity-reordered run — identical waiver verdicts in both orders.
5. **`output_sha256` per-run only.** A test asserts the recorded
   `output_sha256` on a waived record is present (per-run audit trail) and
   is never read by any ordering-decision code path (grep-provable: no new
   code reads `output_sha256` before AC1's iteration order is fixed).
6. **Interleaving stays a named, tested boundary.** A hostile fixture that
   would attempt concurrent `invoke()` calls for two packages is shown
   structurally impossible under the unmodified sequential phase-2 loop (one
   `invoke()` call completes before the next begins); this is asserted as a
   sequencing property, not merely documented.

## Verification Plan

Deterministic pass (`node --test scripts/foreman-line-ci.test.mjs
scripts/ci-reuse.test.mjs`), AC8's fixture matrix (including every
mutate-the-fixture negative named above), and the AC3 before/after
coverage-loudness demonstration are the objective evidence. Beyond those, the
two mandated adversarial reviews (critical/architecture-risk routing) are
directed at these **mandated focus questions** (each gets a field-by-field
assessment; hostile-input probing and mutate-the-fixture discipline are
licensed):

1. **Can ordering ever become a waiver bypass channel?** Implement the naive
   reading — reorder packages so a proximate package's failure output could
   plausibly leak into, precede, or otherwise influence a later package's
   `evaluateWaiver` call — and show AC7's per-package-capture tests exclude
   it. Does any code path read one package's `output` while evaluating
   another's waiver?
2. **Does the D7 pin ever get consumed to exclude, even indirectly?** Audit
   every read of the parsed pin in the implementation; is there any code
   path — including an "optimization" that skips re-checking a
   confidently-non-proximate package — where the pin's absence-of-an-edge
   silently removes a package from `mine`'s execution? (AC1/AC2's
   "ordering never excludes" claim must survive adversarial reading, not
   just the happy-path test.)
3. **Does shard-early-exit genuinely never alter the verdict?** Force an
   early exit in a fixture, confirm the resulting artifact's `skipped`
   entries are the ones `reconcile` already fails on (`unexpected-skip`),
   and confirm no new reconcile branch was added that treats a
   deliberately-skipped tail more leniently than today's logic would treat
   an accidental one.
4. **Is the annotation surface genuinely free of raw captured text?** Try to
   construct a package name, check name, or waiver-rejection layer string
   that smuggles raw output content or a forged `::error`/`::warning`
   sequence into an emitted annotation; confirm `sanitizeField`'s `::` → `: :`
   neutralization and the field-only (never-output) data flow hold under
   hostile input.
5. **Is the D11 diff seam truly the only diff source, and does it fail
   closed on every malformed-base case?** Enumerate: missing
   `GITHUB_EVENT_PATH`, unreadable file, unparseable JSON, present-but-null
   base field, non-hex40 string, all-zeros hex40 — does every one resolve to
   the same fail-closed signal, and does grep confirm no second `git diff`
   invocation exists anywhere in the touched files outside the one new
   export and `ci-reuse.mjs`'s pre-existing evidence-verification diff
   (`:835`, a different, already-reviewed use)?
6. **Does the cost-table re-pin's "deliberate, loud" framing survive a
