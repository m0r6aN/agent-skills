# MRC-08 — HRO-P4a: bounded recovery ladder + provenance-freshness tolerance

## Goal

Close the `hybrid-routing-optimization` charter's **HRO-P4a** row (`docs/goals/hybrid-routing-optimization/charter.md:122`) — *"Implement D8's bounded recovery in the existing resolver; prove exact mapping, refresh limits, approved fallback, and per-parcel hold behavior without guessed substitutions."* — after MRC-06, per the wrapper task row (`docs/goals/model-routing-chain-wrapper/charter.md:61`) and the chain row (`docs/goals/goal-status-report-2026-09-27.md:109`: *"bounded recovery ladder in the resolver + provenance-freshness tolerance … Charter-designated home for the D3 freshness tolerance (HRO-P1 record §5)"*).

The deliverable is **D8's four-step bounded recovery ladder (`charter.md:88-94`) implemented inside the existing resolver seam** — `routing-policy/src/pi-resolver.ts` — never a parallel recovery module (`hro-p0-integration-contract.md:119`: *"The D8 recovery ladder **inside the existing resolver**"*): step 1 exact approved mapping / explicitly registered alias + full D1 eligibility re-check; step 2 at most one coalesced metadata-only refresh per episode + a short version-scoped negative-cache TTL, re-evaluating exact approved mappings only (never approving, tiering, or entitling anything); step 3 the declared-lane fallback walk with a finite attempt cap and deadline, per-target revalidation, and cross-provider attempts only where explicitly declared; step 4 a typed `route_unavailable` outcome with an actionable reason, recorded on the signed receipt, holding only the affected parcel. ### C1 — The ladder seam: API, episode model, configuration inputs

1. **One seam, two exports plus the verdict function** (all in `routing-policy/src/pi-resolver.ts`): `createRecoveryContext(config: RecoveryConfig): RecoveryContext`, `resolveRouteWithRecovery(policy, request, options, episode, context): RecoveryResolution`, and `provenanceFreshnessVerdict(...)`. No other public surface changes except the additive record field (C5) and the barrel re-exports.
2. **`RecoveryContext`** is created once per batch/coordinator lifetime and owns the bounded mutable state: the negative cache (C3.3), the coalesced-refresh memo (C3.2), and the provider-health cooldown stamps (C6.5). All state is in-memory, bounded by the configured limits, and stamped with the **injected** `now: () => string` clock (config) — the resolver never reads time (`ResolveOptions` precedent, `pi-resolver.ts:129-132`). `RecoveryConfig` carries `bounds: RecoveryBounds`, `now`, and the optional inputs: `provenance_freshness_tolerance?: ProvenanceFreshnessTolerance` (C7), `refresh?: MetadataRefreshFn` (C3), `retry_policy?: TransientRetryPolicy`, `health_policy?: ProviderHealthPolicy` (C6).
3. **`RecoveryBounds`** is a typed configuration input — **required** for ladder activation, all four fields finite positive integers (`episode_deadline_ms`, `max_fallback_attempts`, `negative_cache_ttl_ms`, `provider_cooldown_ms`); validation is fail-closed: missing/non-finite/non-positive bounds ⇒ the ladder never runs steps 2–3 and terminates typed with `RECOVERY_BOUNDS_UNCONFIGURED` (C5). **No default values are invented** — bounds come from the caller's configuration, never from code constants.
4. **`RecoveryResolution = { status: 'approved'; receipt; episode } | { status: 'route-unavailable'; receipt; outcome; episode }`** — returned, never thrown, for every routing state (batch-safe; MRC-06's *"the outcome is returned, never thrown"* precedent). The `receipt` is the ordinary signed `RouteReceipt` (approved or stop) produced by the existing `finalizeReceipt`/`signReceipt` path; `episode` is the `RecoveryEpisodeRecord` that also rides the receipt's additive `recovery?` field. Malformed call shapes follow `buildFallbackHandoff`'s fail-closed `TypeError` convention (`pi-resolver.ts:1755-1762`) and authorize nothing.
5. **`RecoveryEpisodeInput = { parcelRef, requested: { lane, registry_key | null }, prior_attempts: readonly PriorAttempt[] }`** — the original request is preserved separately from the selected route (`charter.md:86`: *"Preserve the original request and the actual selected route separately"*); `PriorAttempt = { attempt_ref, provider, failure_class, charge_status: 'no-charge' | 'reconciled' | 'uncertain' }` (C6.1/C6.4).
6. **Monotone episode machine:** step 1 → (2) → 1′ → (3) → (4) with no backward edges (C6.3). A fresh call is a fresh `episode_id` (`documentDigest` of the requested identity + prior attempt refs, `route-receipt.ts:222-224`) but shares the context state (C3.3/C6.5) — the anti-storm mechanism lives across episodes, the ladder state never resets within one.

### C2 — Step 1: exact approved mapping or registered alias + full D1 eligibility re-check

1. **Identity resolution (no guessing).** When `episode.requested.registry_key` is non-null, it resolves through the existing mapping seam only: `piModelContractFor`'s exact matching rule (`pi-resolver.ts:973-975` — registry key, or the mapping's **explicitly declared** `opencodeId` alias) and/or `resolvePiOpenRouterRoute`'s exact lookup (`pi-openrouter.ts:1062-1073`). Regex validates syntax only; an unlisted slug returns the typed `MAPPING_MISSING_REFUSED` (`pi-openrouter.ts:1069-1071`) and is never manufactured into an identity at any step (charter bullet 6, `:136`).
2. **Full D1 eligibility re-check** (`charter.md:40`): role and lane, risk, data classification, required capabilities and tools, context/output capacity, thinking requirements, provider privacy guarantees (transport `data_collection`/`zdr`), remaining budget, and required reviewer independence — evaluated by the **single** existing evaluation (Forbidden: no second predicate implementation), plus `providerRuleGate` (`:826`) for the lane's provider partition. A refusal is recorded with its existing named refusal (never a bare non-selection).
3. **Freshness gate (C7 semantics) at every eligibility re-check:** `stale` evidence rejects the target with `FRESHNESS_STALE_REFUSED` (`route-receipt.ts:47`); `unknown` evidence is carried as honest unknown — recorded, never assumed current, never rejected on its own (HRO-P1 §5); `fresh` proceeds.
4. **Step-1 success** emits the ordinary approved receipt for the requested target (its declared fallback pair evaluated exactly as today — denied, never downgraded) and the episode record's `attempted[0]` carries the requested identity with `outcome: 'approved'`.
5. **Step-1 failure** (mapping missing/incomplete/protocol-incompatible, an eligibility refusal, or `stale` evidence) is recorded per-attempt with its named refusals and triggers step 2 when the failure is an evidence failure (C3) or step 3 otherwise. When `requested.registry_key` is null, step 1 is the ordinary `resolveRoute` selection; a `status: 'stop'` receipt is step-1 failure.

### C3 — Step 2: one coalesced metadata-only refresh per episode + version-scoped negative-cache TTL

1. **Trigger and permission.** *"If evidence is missing or stale"* (`charter.md:91`): a step-1 failure caused by missing evidence (`unknown` provenance / missing mapping evidence) or `stale` evidence permits **at most one** `refresh` invocation per episode. Without a `refresh` seam, or after the single invocation, the ladder records `result: 'not-permitted'` and proceeds to step 3. The deadline is enforced at the step boundary against the injected clock: a refresh that returns after `episode_deadline_ms` is discarded, recorded `RECOVERY_DEADLINE_EXCEEDED`, and never used.
2. **Coalescing across episodes.** The context's refresh memo keys on `(requested_key, evidence_version)`: at most **one** `MetadataRefreshFn` invocation per key/version window across all episodes sharing the context; concurrent or repeated misses attach to the recorded result (`RefreshProvenance.coalesced: true`) instead of invoking the seam again. Check-and-invoke is atomic within the single-threaded evaluator, so no double-invoke window exists.
3. **Version-scoped negative cache.** Repeated mapping misses are memoized per `(requested_key, evidence_version)` with TTL `bounds.negative_cache_ttl_ms` (injected-clock expiry — the entries expire, charter bullet 7): a miss inside the TTL is served from the negative cache (`refresh.result: 'negative-cached'`, no seam call); after expiry the next episode may attempt the single refresh again; a change of `evidence_version` (the catalog/mapping content identity — e.g. the provenance `content_hash`, `pi-openrouter.ts:65-66`) immediately re-arms the entry. The negative cache gates the **refresh trigger only** — the fallback walk and its dynamic revalidation always run (D4: *"Revalidate dynamic budget, availability, and independence rather than trusting stored authorization"*, `charter.md:60`).
4. **Metadata-only; refresh never approves.** `MetadataRefreshFn` returns `MetadataRefreshResult` = `{ status: 'refreshed'; provenance: DeclaredEvidence<PiOpenRouterProvenance>; entries: Record<string, { available: boolean }> } | { status: 'unavailable'; reason: string }`. The ladder consumes exactly two things from it: the provenance (C7 verdict — a refreshed document that is itself `stale` stays `stale`, fail-closed) and availability facts for **re-evaluating exact approved mappings** (charter:91). An entry naming a key with no approved mapping is recorded as a discovered candidate and **never** becomes a route, mapping, tier, fallback, or entitlement (`charter.md:91`; D3 `:52`).
5. **Re-evaluation runs exactly once.** After the single refresh, step 1′ re-evaluates exact approved mappings (with the refreshed evidence) exactly once; success emits the approved receipt (the episode record keeps the refresh provenance), failure proceeds to step 3. There is no path back to step 2 (C6.3).

### C4 — Step 3: the declared-lane fallback walk (finite cap + deadline + per-target revalidation)

1. **Walk set = declared routes only.** The walk enumerates only the fallback routes **already declared for the authorized lane** in the policy's `lane_routes` structure (`LaneRoute`, `types.ts:348-355`), in declaration order: each lane entry's declared `primary` then `fallback` route refs, resolved exactly as the validator resolves them (never a raw ref as a model value). An undeclared candidate is never attempted (charter:92); *"Different model/provider selection is a fallback, not an alias"* (`:95`) — every walk target is recorded with role `'fallback'`/`'cross-provider'`, never as an alias of the request.
2. **Finite cap and deadline.** At most `bounds.max_fallback_attempts` targets are attempted (each attempt and each permitted transient retry counts); before each attempt the injected clock is checked against `episode_deadline_ms`; cap exhaustion records `RECOVERY_ATTEMPT_CAP_EXHAUSTED`, deadline expiry records `RECOVERY_DEADLINE_EXCEEDED`, and either ends the walk into step 4. The walk visits each declared target at most once (a visited set — no cycles, `charter.md:95`).
3. **Per-target revalidation.** Every target passes the **full** D1 re-check (C2.2) — provider, protocol, capabilities, data handling (transport), independence, and remaining budget (`charter.md:92`) — with the C7 freshness gate. An ineligible target is skipped **with its named reasons** (charter bullet 7: *"Ineligible fallback candidates are skipped with reasons"*) and the walk continues to the next declared target.
4. **Cross-provider only when explicitly declared.** A target on another provider than the authorized route's is attempted only when all three hold: (a) the lane's `provider_rule` is not `pinned-provider` (`types.ts:242-243` — *"a partition no fallback crosses"*); (b) the target is a declared route primary for the lane (the `cross-provider-attempt` rule of `buildFallbackHandoff`, `pi-resolver.ts:1804-1812`); (c) the transition is recorded as a `cross-provider-attempt` handoff event per `FallbackHandoffPlan.cross_provider` (`route-receipt.ts:154-158`: `new-recorded-attempt-from-durable-handoff`, `silent_continuation: 'never'`). If any condition fails the target is **excluded** (recorded `skipped`, reason naming the missing declaration) — fail-closed, never an implicit default (*"No universal DeepSeek, Sonnet, or other default is intrinsically safe for all roles"*, `charter.md:92`).
5. **First eligible target wins;** the chosen fallback is recorded (`RecoveryEpisodeRecord.chosen_fallback`) and emitted through the ordinary receipt path (`finalizeReceipt` with the chosen target evaluated as a primary and its own declared fallback pair — the declared-pair rule of `buildFallbackHandoff` preserved). The approved receipt's `evaluations` carry every attempted candidate and its refusals (A3: *"every ranking input and the chosen binding, not only the winner"*, `route-receipt.ts:5`).

### C5 — Step 4: typed `route_unavailable` + per-parcel hold + the recovery record

1. **One terminal shape, aligned with MRC-06 (f)** (`docs/specs/active/MRC-06-hro-p4-pi-entry.md:141`), defined in `routing-policy/src/route-receipt.ts` with the identical field set: `RouteUnavailableOutcome = { code: 'ROUTE_UNAVAILABLE', parcelRef, requested: { lane, registry_key | null }, attempted: readonly { identity, refusals }[], refusals: readonly RefusalEntry[], reason: string, hold: 'parcel-held' }`. A pinned field-set control asserts the exact keys (the alignment control); if MRC-06's landed type diverges, Stop-and-Report #6 applies — the entry's type is never edited here. `reason` is actionable (names the exhaustion condition and the next action — e.g. *"no eligible route for '<slug>' after N declared fallbacks; await G-FRESH-TOL / submit the mapping for review"*), and `refusals` names every terminal-cause refusal (per-attempt refusals ride `attempted`).
2. **Hold semantics (per-parcel).** `hold: 'parcel-held'` marks exactly the `parcelRef` named in the episode input; the resolution is **returned**, never thrown, so the batch runner continues independent parcels under its own dependency rules and *"never mark[s] blocked work complete or crash[es] the whole batch because one model cannot be resolved"* (`charter.md:93`; charter bullet 7: *"exhaustion holds only affected/dependent work"*). A concurrent episode for a different `parcelRef` is unaffected (control).
3. **Recorded, durably.** The `RecoveryEpisodeRecord` (`kind: 'recovery-episode-record'`, `schema_version: 1`) carries exactly D8's five record classes (`charter.md:95`): `attempted: AttemptRecord[]` (attempted candidates + rejection reasons + outcomes), `refresh: RefreshProvenance` (refresh provenance incl. the `DeclaredEvidence<PiOpenRouterProvenance>` value and the coalescing/negative-cache result), `chosen_fallback`, `freshness` (verdict + `age_ms` + `tolerance_ms`), and `terminal: RouteUnavailableOutcome | null`. It rides the signed receipt as the additive optional `recovery?` field — covered by `signReceipt`/`verifyReceiptSignature` (`route-receipt.ts:231-241`), and durable wherever the receipt is persisted (MRC-06's entry record persists the full signed receipt, its C5.3). The D10 structured reason/outcome semantics (`mapping_missing`/`catalog_refresh_failed`/`approved_fallback_selected`/`route_unavailable`, `charter.md:107`) are carried as data on these fields; label-to-schema reconciliation is MRC-12's (Out of Scope).
4. **Step-4 terminal emits the ordinary `status: 'stop'` receipt** carrying the terminal's refusal names in `stops` **plus** `recovery` (record + `terminal`), and returns `status: 'route-unavailable'` with the outcome. No crash, no silent substitution, no unaccounted duplicate dispatch (charter bullet 5, `:135`).

### C6 — Honesty rules: retries, reconciliation, cycles, cooldown

1. **Failure classes are opaque, validated data.** `PriorAttempt.failure_class` arrives from the execution-side provider-error validation (Out of Scope) and is recorded verbatim, never folded (the distinctness rule of `types.ts:524-525`) and never re-derived from error strings or HTTP codes (the ladder contains no such inspection — static control). Distinct classes produce distinct recorded values.
2. **Transient retries only per provider contract.** A prior transient failure on a walk target permits **at most one** re-attempt of that target, only when `retry_policy.retryable(failure_class)` is true (the provider contract + existing retry policy, injected); without a `retry_policy` nothing ever retries. Every retry is a separate `AttemptRecord` (never hidden — D5: *"without hiding retries"*, `charter.md:68`) and counts against `max_fallback_attempts`.
3. **No reset, no cycles.** Within an episode the machine only advances (C1.6): one refresh, one re-evaluation, each target at most once, terminal sticky. Exhaustion never re-enters the walk and never re-arms the negative cache entry early.
4. **Uncertain charge ⇒ reconcile before redispatch.** If any `prior_attempts` entry has `charge_status: 'uncertain'`, the ladder performs **no** redispatch: steps 2–3 are not entered, and the terminal names `RECONCILIATION_REQUIRED` with `hold: 'parcel-held'` (charter:95; charter bullet 5). Only `no-charge`/`reconciled` entries allow the episode to proceed. Reconciliation itself is the settlement seam's (Out of Scope).
5. **Minimal bounded provider-health cooldown (none exists — C0).** A `health_policy.unhealthy(failure_class)` verdict on a recorded attempt stamps that attempt's provider with a cooldown until `now + bounds.provider_cooldown_ms`; while active, walk targets on that provider are skipped with `PROVIDER_COOLDOWN_ACTIVE` and the skip is recorded; the stamp expires on the injected clock (*"without permanently hiding recovered providers"*, `charter.md:95`), and the stamp map is bounded. This is the entire breaker surface — no more.

### C7 — Provenance-freshness tolerance: typed input, fail-closed default, G-FRESH-TOL

1. **The typed configuration input.** `RecoveryConfig.provenance_freshness_tolerance?: ProvenanceFreshnessTolerance` where `ProvenanceFreshnessTolerance` is a non-negative finite integer — milliseconds of policy grace beyond an evidence document's own declared `valid_until` (`pi-openrouter.ts:63-64`). It is consumed only from this input; **no value, default, or fallback constant exists in code** (never invent a number).
2. **`provenanceFreshnessVerdict(provenance, now, tolerance): FreshnessVerdict`** (`'fresh' | 'stale' | 'unknown'`):
   - provenance absent ⇒ `'unknown'` — P1's honest unknown (`hro-p1-mapping-contract-2026-09-27.md:82`: *"Provenance absence remains honest unknown"*): never assumed current, recorded as unknown, **never rejected on its own** (preserving the shipped mappings' behavior — provenance is absent on them by design, `hro-p1-mapping-contract-2026-09-27.md:44`);
   - `now ≤ valid_until` ⇒ `'fresh'` (within the evidence's own declared validity);
   - `now > valid_until`, tolerance **set** ⇒ `'fresh'` when `now − valid_until ≤ tolerance` (recorded with `age_ms` and `tolerance_ms` so the grace is visible), else `'stale'`;
   - `now > valid_until`, tolerance **unset** ⇒ **`'stale'` — the fail-closed default: zero policy grace beyond the evidence's own declared validity.** Unparseable timestamps are `'stale'` (fail-closed).
3. **Enforcement.** The verdict runs at every eligibility re-check (steps 1, 1′, 3): `'stale'` ⇒ the target is rejected `FRESHNESS_STALE_REFUSED` — charter bullet 1's *"stale catalogs beyond policy tolerance … are rejected"* (`:131`) — and stale/`unknown` evidence is what permits the step-2 refresh. The verdict never approves anything by itself.
4. **The ratification flag — G-FRESH-TOL (owner/coordinator).** The named gate records the ratified tolerance value in the owning record; until it exists, callers pass the input unset and behavior is the fail-closed default above. When G-FRESH-TOL lands, activation is a configuration change (callers pass the ratified value) — no code change, and the ladder's controls cover both states (Required Tests). This spec neither proposes nor implies any particular value.

### C8 — Data class, spend, rollback; review and acceptance

**Data class:** internal — the episode record carries repo-internal routing metadata, catalog metadata (availability facts + provenance timestamps/hashes), and opaque failure-class strings; no credentials, no host paths, no provider payloads (the receipt's no-secret property, `route-receipt.ts:8-15`). **Spend:** zero — no provider call, network call, or paid experiment is made or implied (the refresh is an injected metadata seam; tests use synthetic fixtures); any live smoke stays behind G-LIVE. **Rollback:** revert the additive hunks in `route-receipt.ts`/`types.ts`/`index.ts` and delete `pi-resolver.ts`'s recovery section and the new test file; `resolveRoute` and every consumed seam are untouched, so the pre-parcel behavior is restored exactly. **Review:** two independent adversarial reviews (wrapper D6 `charter.md:34`; MRC-08 row `:61`); reviewers never fix or commit.
