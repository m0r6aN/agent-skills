### C1 — Trigger and evidence discipline (D9's "verified provider model missing from local configuration")

1. **The trigger.** `buildConfigRepairProposal(input, { now })` fires exactly when (a) the model is **verified** — it holds an approved mapping (the policy's `PiModelContract`, exact fields) **and** a named catalog observation (C2.2) — and (b) it is **missing from local configuration** — absent from the supplied `LocalConfigView` (the current `enabledModels` membership under the `provider:model` spelling rule, and/or the declaration-document entry at the contract locator). A **discovered-but-unapproved** model never triggers anything (charter bullet 8 first sentence: *"A newly discovered but unapproved model remains ineligible"*): no approved mapping ⇒ `EVIDENCE_INSUFFICIENT_REFUSED`, and no evidence record can manufacture a mapping (negative control).
2. **Pure, side-band, typed inputs.** The module is pure — no fs, no network, no clock reads (`now` injected, the PMC resolver pattern `pi-resolver.ts` module purity); every input is a typed field or opaque bytes: `VerifiedModelEvidence { mapping: MappingProvenance; catalog: CatalogEvidence; freshness: 'fresh' | 'stale' | 'unknown'; trigger: { source_refusal: string; episode_ref?: string } }`, `LocalConfigView { documents: readonly SourceState[] }` where `SourceState = { role: 'pi-settings' | 'pi-models-declaration'; text: string; content_hash: string; observed_at: string }` (bytes + hash supplied by the caller — the MRC-06 C2 input-seam pattern; the module never opens a host file).
3. **Evidence completeness (D9: the diff carries "catalog evidence and explicit mapping provenance").** `CatalogEvidence` names what was observed and from where (`observed_via: 'metadata-refresh' | 'catalog-snapshot'` + a `ProvenanceRef`); `MappingProvenance` carries the four HRO-P1 fields exactly plus a `mapping_source: ProvenanceRef` naming the policy mapping record. If either named source is absent, the builder **refuses** (`EVIDENCE_INSUFFICIENT_REFUSED`, returned) — a proposal without evidence is never emitted. The freshness envelope (`DeclaredEvidence<PiOpenRouterProvenance>`) may itself be absent = honest unknown (C2.2).
4. **Freshness is carried, never re-derived.** `freshness` arrives as data under MRC-08's `FreshnessVerdict` name (`'fresh' | 'stale' | 'unknown'`, its C7.2) and is recorded verbatim on the artifact; it never rejects on its own (`unknown` stays honest unknown — `hro-p1-mapping-contract-2026-09-27.md:82`) and the freshness policy stays the resolver's (MRC-08 C7.3).
5. **Already-configured ⇒ no proposal.** When the model is present in the supplied view (enablement member and/or entry present), the builder returns `{ status: 'no-action' }` — running the builder repeatedly never stacks proposals (idempotence, C2.4).

### C5 — The reference apply over a mock/temp writer (the provable half)

1. **`planConfigRepairApply(proposal, current: SourceState): ApplyPlan` — pure.** Order: (1) recompute `proposal_digest` (`PROPOSAL_DIGEST_MISMATCH_REFUSED` on tamper); (2) role/scope match against the bound target (`TARGET_SCOPE_MISMATCH_REFUSED`); (3) source validity — the current bytes must parse as the expected document shape; an invalid source is a **repair failure** (`SOURCE_INVALID_REFUSED`) and the source is never replaced (D9 `:103`); (4) concurrent-change detection — `current.content_hash` must equal the proposal's recorded `source_state` hash for the role, else `SOURCE_HASH_MISMATCH_REFUSED` (a lock-based writer maps the same duty onto its lock and records its own refusal — the checklist carries the duty, the reference implements hash mode); (5) merge — apply the minimal change set and return `result_text` with every unrelated byte preserved (unrelated fields and credential references byte-equal), plus `backup_text` (the exact original bytes); (6) idempotence — when the change set is already present, return `{ status: 'already-applied' }` with zero writes.
2. **`writeConfigRepairAtomically(plan, target: { path: string; root: string }, seam: ConfigWriteSeam, hooks?: { on_applied?: () => void }): ApplyOutcome` — I/O only through the injected seam.** `ConfigWriteSeam = { read; writeTemp; rename; remove; exists }`. Order: absolute-root + containment guards **before any seam call** (the `assertAbsoluteRoot`/`assertContainedRootPath` family, `dispatch/src/approval-cli/index.ts:73-95`); write result to a temp file beside the target; persist the backup; rename temp → target; on any failure restore the backup and remove the temp (`rolled-back`, original intact, **no partial output**); `hooks.on_applied` fires **exactly once and only after** the successful swap (the D9 *"refresh relevant cache versions only after a successful apply"* ordering, carried as data). Outcomes: `applied` | `already-applied` | `refused` | `rolled-back`.
3. **The seam is the mock/temp writer ruling D permits.** The module performs no I/O itself (static control); tests bind `ConfigWriteSeam` to a real temp directory (`os.tmpdir()`), which is what makes invalid-file, concurrent-edit, interrupted-write, rollback, duplicate-update, and preservation provable **without touching host config**.
4. **Duplicate updates are idempotent end-to-end.** A second `writeConfigRepairAtomically` over an applied result returns `already-applied` and performs **zero** seam writes (call counter) — the bullet-8 "duplicate updates" item, paired with C2.4's proposal-side idempotence.
