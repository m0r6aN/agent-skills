# MRC-06 — HRO-P4: the supported Pi/parcel entry point

## Goal

Close the `hybrid-routing-optimization` charter's **HRO-P4** row (`docs/goals/hybrid-routing-optimization/charter.md:121`) — *"Wire the supported Pi/parcel entry point; validate configuration, actual host model selection, parcel preservation, declared fallback, and unavailable-provider rejection."* — after MRC-05, per the wrapper task row (`docs/goals/goal-status-report-2026-09-27.md:107`: *"Pi/parcel entry point wiring: config validation, actual host model selection, parcel preservation, declared fallback, unavailable-provider rejection … after MRC-05 because its 'actual host model selection' validation consumes the decision receipt"*).

The **supported** entry path is the charter A1 one: *"A dispatched Pi session is authorized only by an **approved route receipt** emitted by the resolver"* and *"Direct or default Pi invocation is not a Foreman execution path"* (`docs/goals/pi-model-configuration/charter.md:108-120`). Today the seams exist but nothing composes them: `resolveRoute`/`verifyLaunch`/`buildFallbackHandoff` have **test callers only** (no production caller wires parcel dispatch → resolver → launch boundary → Pi session). This parcel builds that composition — the entry module — and the boundary checks the HRO-P4 row names, without reimplementing anything PMC-P2 already enforces (see *Existing Patterns To Follow*, first table).

Scope, exactly the HRO-P4 row: **(a)** the Pi/parcel entry wiring (parcel dispatch → Pi session with its approved route); **(b)** configuration validation — **validate, never write** (ruling D, `goal-status-report-2026-09-27.md:83`: *"HRO-P4b is proposal-only … apply stays with PMC's authorized writer"* — so P4 validates the host Pi configuration read-only); **(c)** actual host model selection validation (the host-selected model matches the approved route receipt; built on MRC-05's `verifyExecutedIdentity`); **(d)** parcel preservation (parcel content survives the entry path unchanged); **(e)** declared fallback use only (the one typed fallback the approved route declares — nothing else); **(f)** unavailable-provider rejection typed (the charter's `route_unavailable` outcome with an actionable reason, the parcel held).

This closes charter verification bullet 10 (`charter.md:140`, *"Quoted CLI arguments remain data; malformed/duplicate frontmatter is handled deliberately; valid parcel content survives read/write round trips; failed writes do not leave partial output"*) at the entry boundary, and contributes to bullets 2 (`:132`, declared fallbacks enforce the same constraints), 5 (`:135`, truthful outcomes / only approved recovery), 8 (`:138`, *"Routing never writes global Pi configuration"*), and 12 (`:142`, package checks) — the recovery-ladder half of 5/7 stays MRC-08's.

`verification_class: equivalence-provable` — every behavior is bounded to a named contract item with deterministic, falsifiable controls; the consumed seams (PMC-P2's resolver/launch boundary/host-settings projection, MRC-05's decision receipt) are proven unchanged by their own suites passing with zero edits.

### C1 — Entry wiring: the supported path from parcel dispatch to a Pi session (scope a)

1. **The composition (the wiring).** The supported sequence is: `prepareDispatch`/`executeDispatch` (the parcel flow, `dispatch/src/approval-cli/index.ts:273,:480`) → **`preparePiEntry(input, options)`** (this module) → the launcher verifies the launch boundary at session start and runs the session on `session_request` (existing PMC-P2 coverage — see *Existing Patterns To Follow*) → **`verifyHostModelSelection`** (C3.3) at/after selection → **`verifyExecutedIdentity`** on `ResultEnvelope.modelRef` at result time (MRC-05 C4.4, consumed) → **`useDeclaredFallback`**/**`writePiEntryRecord`** as needed (C4/C5). The entry is exported as the supported surface via `dispatch/src/index.ts` (additive). It is not invoked inside `executeDispatch` (Forbidden) — the dispatch flow hands it `specText` and the decision record's bindings.
2. **`preparePiEntry(input: PiEntryInput, options: PiEntryOptions): PiEntryResult`** — pure (no fs, no network, no clock reads; `options.now: () => string` injected, the PMC resolver pattern). `PiEntryInput` is fully typed and carries the caller's authority decisions (boundary-routing D7: Foreman decides role/risk/data-classification/independence/budget — the entry validates, never decides): `parcel: { ref, path, text }`, `policyText: string` (the exact routing-policy bytes), `decision: ReplayBindings` (MRC-05's named shape), `routeRequest: RouteRequest` (the resolver vocabulary, `routing-policy/src/pi-resolver.ts:96-127`), `hostSettings: HostSettingsSnapshot`, `max_age_ms: number` (the owner-accepted freshness bound).
3. **Step order (each step's failure is typed and bounded):** (1) policy bytes → `yaml` parse + `validatePolicy` (consume-as-is) + digest binding against `decision.policy_digest` (C1.4); (2) effective-requirements consistency (C1.5); (3) `resolveRoute(policy, request, { issued_at: now() })` (consumed unchanged) — a `status: 'stop'` receipt is the C6 terminal, never a launch; (4) `verifyLaunch(receipt, { requested_lane: request.lane, at: now(), max_age_ms })` (consumed unchanged) — any refusal is the C6 terminal carrying the `LAUNCH_REFUSALS` names; (5) identity bridge + decision agreement (C3.1–C3.2); (6) host-configuration validation (C2); (7) emit `PiEntryPackage { receipt, sessionRequest, parcel, identity, fallbackHandoff, verdicts }`.
4. **Policy binding (one named digest formula).** The supplied policy bytes' SHA-256 must equal `decision.policy_digest.content_digest` and the decision's `policy_digest.version` must be the pinned policy ref; a mismatch throws typed `PiEntryError('POLICY_DIGEST_MISMATCH', …)` — the entry never resolves a route against policy bytes other than the ones the decision was made under. If the decision side's digest formula is not raw-bytes SHA-256, the entry reuses the decision side's **named** formula (never a second one) — see Stop rule 4.
5. **Effective-requirements consistency (the decision record is the recorded authority).** Exact-match rules between `routeRequest` and `decision.effective_requirements` (MRC-05's C2/C4.1 named fields): `required_inputs` deep-equal (canonical order; absent↔absent — D8's "omitted = `['text']`" equivalence is the two systems' shared default, never re-derived here); `required_thinking_level` exact, absent↔absent; `expertise` exact, absent↔absent; floors per C3.4. Any mismatch throws typed `PiEntryError('REQUIREMENT_MISMATCH', …)` naming the field — the entry never repairs, averages, or silently re-derives a requirement.

### C2 — Configuration validation: validate, never write (scope b; ruling D)

Pure read-only validation over the supplied `HostSettingsSnapshot` (the input seam stands in for the launcher's host read; the entry never reads or writes a host file):

1. **Provider registration.** `providers` must contain `providerKey === receipt.route.provider`; else refusal `HOST_PROVIDER_UNREGISTERED_REFUSED` (the host cannot serve the approved route).
2. **Endpoint conformance.** For OpenRouter routes, the registered `providers['openrouter'].baseUrl` must equal `receipt.route.openrouter_constraints.base_url` (the `pi-openrouter.ts` contract const — the SCF-3 comparator); else refusal `HOST_ENDPOINT_DIVERGENT_REFUSED`. For a route whose receipt carries no contracted endpoint, **no endpoint claim is made** (unknown stays unknown; the resolver's own `ENDPOINT_DIVERGENCE_REFUSED` resolve-time check is existing coverage, not re-run here).
3. **Model enablement.** The approved route's host-enabled spelling — `` `${route.provider}:${route.primary.model}` ``, composed from the receipt's own bound values exactly as `hostSpelling` composes them (`routing-policy/src/host-settings-proposal.ts:161-164`) — must be a member of `enabledModels`; else refusal `HOST_MODEL_NOT_ENABLED_REFUSED`. The composition is pinned by a lockstep parity control against the committed PROPOSED artifact's `enabledModels` add values (`docs/goals/pi-model-configuration/pmc-p2-pi-host-settings-PROPOSED-2026-09-26.json`); if the composition does not reproduce at build time, stop (Stop rule 6) — a lookup spelling is **never** derived from a registry key or host id.
4. **Never writes.** The module contains no host path, no settings write, and no proposal emission (ruling D; the no-host-path control in the tests). When the declared fallback becomes the session route (C4), the same three checks run against the fallback identity.

### C3 — Actual host model selection validation (scope c; built on MRC-05's `verifyExecutedIdentity`)

1. **Identity bridge (D2 distinct-values; per-field exact).** `decision.selected_identity` ↔ the approved route's `PiModelContract` map field-for-field: `registry_key`↔`registry_key`, `pi_host_model_id`↔`opencode_id` (the Pi-host identifier designation, HRO-P0 §1.2), `provider_local_id`↔`provider_local_id`, `protocol`↔`protocol`; null↔null; any divergence (including null↔value) refuses `IDENTITY_MISMATCH_REFUSED` — values are never filled in, normalized, or derived (Stop rule 3).
2. **Decision agreement at entry (the `verifyExecutedIdentity` build-on).** `verifyExecutedIdentity(decision, receipt.selection.chosen)` (MRC-05 C4.4, consumed) must reproduce — the approved route's chosen identity **is** the dispatch decision's selected identity; its typed refusal (`REPLAY_REFUSED`, binding `selected_identity`) rides the entry refusal detail as `SELECTION_MISMATCH_REFUSED`. A cross-version decision record (C4.5) refuses the same way and is never silently accepted. The launch package is emitted only when both halves agree.
3. **Host-selection request and its validation.** `sessionRequest` carries `{ lane, registry_key, host_model_id, provider_local_id, protocol, thinking_level, route_receipt_id }` where `host_model_id` is the bridge's `pi_host_model_id`; a null host id refuses `HOST_MODEL_UNBOUND_REFUSED` (fail closed — the session cannot be told which host model to select). `verifyHostModelSelection(entry, observed: HostSelectionObservation)` validates the **actual** host selection by exact string equality `observed.host_model_id === sessionRequest.host_model_id`, else `HOST_MODEL_MISMATCH_REFUSED` — a registry-key or provider-local-id match never passes as a host-id match (the C4.4 no-aliasing rule applied to the host namespace). At result time the executed identity reconciles through `verifyExecutedIdentity(decision, modelRef)` directly (no wrapper, no second verdict shape).
4. **Resolved thinking level (MRC-05 C5's handoff; carried as data).** `sessionRequest.thinking_level = { value, source }` where `value` is the decision's resolved level — `effective_requirements.required_thinking_level` when bound, else the single named default formula of MRC-05 C2.2 (`THINKING_DEFAULT_BY_CLASS[effective_requirements.routing_class]`) with `source: 'class-default'` — validated against the closed `THINKING_LEVELS` vocabulary. The launcher applies it **where the plane supports it**; the entry makes no application claim and invents no Pi-enum mapping (H-PI hold). Floors (D7 authority): when `decision.derived_context_floor.required_context_tokens`/`required_output_tokens` are bound, `routeRequest`'s floors must be **≥** the bound floors (SPEC-CONVENTION §4.9 upward-only rule, `docs/SPEC-CONVENTION.md:142-181`), else `REQUIREMENT_MISMATCH`; when null, the caller's declared floors stand (no floor was recorded — unknown stays unknown).

### C4 — Declared fallback use only (scope e)

1. **The only permitted route change** at the entry is to `receipt.route.fallback` — the single declared typed fallback the resolver already evaluated, rankability-checked, and identity-verified (A2 *"denied, never downgraded"*; PMC-P2 record §2 items 3/5) — and only through `useDeclaredFallback(entry, event: HandoffEvent, options)`:
   - the `HandoffEvent` (`primary-degraded` \| `fallback-failed` \| `cross-provider-attempt` with `{ binding_id, observed }`, `routing-policy/src/pi-resolver.ts:1612-1619`) must name the declared pair — `buildFallbackHandoff(receipt, event, options)` (consumed unchanged) throws on any out-of-pair `binding_id` and the entry wraps that as `UNDECLARED_FALLBACK_REFUSED` (nothing authorized);
   - the returned fallback entry re-runs C2 and C3 against the fallback identity (its `PiModelContract` from `piModelContractFor`, consumed — the record: *"Pi-side per-model contract looked up … for primary and fallback alike"*), producing a fresh `sessionRequest` for the fallback;
   - `cross-provider-attempt` is a **new recorded attempt** from the durable handoff, never a silent mid-turn continuation (`continuation: 'refused-mid-turn'`, D3; `FallbackHandoffPlan.cross_provider`).
2. **No third model, no walk.** Any request to select a model outside {primary, declared fallback} refuses `UNDECLARED_FALLBACK_REFUSED`. `fallback-failed` on the declared fallback is terminal: `ROUTE_UNAVAILABLE` (C6) — *"if both fail, the parcel stops and reports"* (PMC charter D8, `docs/goals/pi-model-configuration/charter.md:59`). No refresh, no attempt caps, no cycle handling here (MRC-08).

### C5 — Parcel preservation (scope d) and the entry record

1. **Opaque carry.** `parcel.text` is carried byte-exact into `PiEntryPackage.parcel` and into the entry record, with `parcel.sha256` = SHA-256 of the exact input bytes. The entry never re-serializes, trims, re-orders, or prepends frontmatter (D6: *"Do not … prepend duplicate frontmatter"*); frontmatter is the dispatch flow's parse domain (`parseFrontmatter` refuses malformed input `SPEC_INVALID_FRONTMATTER` at `prepareDispatch` time), and at the entry a malformed or duplicate-`---` document is **data** — carried unchanged, deliberately (charter bullet 10, `charter.md:140`).
2. **Data-only inputs.** Every input is a typed field or an opaque string (parcel path/text, policy bytes) — no interpolation of argument text into executable code, no shell, no `eval`/`Function` (control: the module's import manifest is node builtins + the named seams only).
3. **The entry record (`PiEntryRecord`, `kind: 'pi-entry-record'`, `schema_version: 1`)** is the durable record the HRO-P4 row requires ("record it"): `status: 'launchable' | 'route-unavailable'`, `parcel { ref, path, text, sha256 }`, `policy { version, content_digest }`, `decision_bindings` (the consumed `ReplayBindings` echo), `route_receipt` (the full signed resolver receipt — no-secret by PMC-P2's machine-checked property), `session_request` (or `outcome` for the terminal), `host_config_verdict`, `fallback_handoff`, `created_at` (injected clock). No secret, credential, or host path may appear in it (D2; the PMC-P2 no-secret scan pattern).
4. **`writePiEntryRecord(result, recordPath, { repoRoot })`** — the only write in this parcel. Absolute-root and containment guards first (the `assertAbsoluteRoot`/`assertContainedRootPath` family, `dispatch/src/approval-cli/index.ts:73-95`); collision handling explicit: an existing target refuses `RECORD_EXISTS_REFUSED` (the `writeApprovalRecord` refuse-overwrite pattern, `approval/src/approval-record.ts:73-81`); the write is atomic — temp file in the target directory + rename, and on any failure the temp is removed and the target left absent (no partial output; the `approve-flow` rollback pattern, `approval/src/approve-flow.ts:3-9`). Round-trip control: write → read → `parcel.text` byte-equal and `parcel.sha256` equal.

### C6 — Unavailable-provider rejection typed: the `route_unavailable` terminal (scope f)

1. **One terminal outcome.** When the parcel cannot enter its Pi session, `preparePiEntry`/`useDeclaredFallback` return `{ status: 'route-unavailable', outcome: RouteUnavailableOutcome }` — never a crash, never a silent substitution: `RouteUnavailableOutcome = { code: 'ROUTE_UNAVAILABLE', parcelRef, requested: { lane, registry_key | null }, attempted: readonly { identity, refusals }[], refusals: readonly RefusalEntry[], reason: string, hold: 'parcel-held' }`. `ROUTE_UNAVAILABLE` is the charter's own typed outcome name (D8 step 4: *"return a typed `route_unavailable` outcome with an actionable reason, record it, and hold the affected parcel. Continue independent parcels when dependency rules allow; never mark blocked work complete or crash the whole batch"*; the events vocabulary already carries `ROUTE_UNAVAILABLE`, MRC-05 C3.3).
2. **Terminal triggers (each named in `refusals`):** the resolver's `status: 'stop'` receipt (its `stops` names ride the outcome — today's shipped evidence stops every lane fail-closed, PMC-P2 record §5); any `verifyLaunch` refusal (`LAUNCH_REFUSALS` names — missing/stale/lane-mismatched/unsigned/tampered/unattested); any C2 config refusal (unregistered provider, divergent endpoint, model not enabled — the unavailable-provider rejection); C3 refusals (`IDENTITY_MISMATCH_REFUSED`, `SELECTION_MISMATCH_REFUSED`, `HOST_MODEL_UNBOUND_REFUSED`); C4's fallback exhaustion (`fallback-failed`). The outcome records requested-vs-attempted identities and reasons (D10's *"requested and selected provider/model, reason, and next action"* semantics; rendering is MRC-12's).
3. **Hold semantics.** `hold: 'parcel-held'` marks the affected parcel held; batch continuation is the caller's (dependency rules); the outcome is written into the entry record (C5.3) so the hold is durable and inspectable.
4. **No recovery here.** The terminal is final for this entry attempt; only the ONE declared fallback (C4) may precede it. The bounded ladder is MRC-08's.
