### C1 — Chain-slot resolution (the pre-shaping hazard) and the coexistence invariant

1. **The fix — tip-derived allocation at write time.** In `executeDispatch`, the Stage-C draft's `sequence` and `prevHash` are derived from the **chain tip at write time**, never from a literal slot and never from the prepare-time Stage-B read alone: `sequence = tipSequence + 1`, `prevHash = tip.hash`, locator `receiptPath(workflowId, sequence, 'C', 'DispatchOrder')`. The tip is read with the discipline already in the tree: the evaluator's `readChainState` (`dispatch/src/routing-eval/index.ts:244-286`, exported for reuse — chain-directory scan per `CHAIN_FILE_RE` `:225`, highest sequence wins, tip hash verified) — the same rule the Stage-E emitter applies at its seam (`integration/src/receipt.ts:115,:142-143`) and `findHighestSequenceFile` applies for prior-receipt resolution (`dispatch/src/query/index.ts:231-251`). The change is exactly the three literals at `dispatch/src/approval-cli/index.ts:535,:551,:552`.
2. **Equivalence at the legacy tip.** When no entries landed after the Stage-B receipt, the tip IS Stage-B (`sequence: 1`), so the derived values are exactly `2` and the Stage-B hash — byte-identical to today's outcome (the literal `000002-C-dispatch-order.json` at the legacy tip is preserved by construction, not by special case).
3. **Correlation wiring.** `prepareDispatch` builds one `CorrelationContext` (`contracts/src/correlation.ts:37-43`) — `correlationId` = the inherited `priorCorrelationId` (W4-P0 discipline, `:373,:543-546`), `sessionId`/`runId` minted fresh per dispatch run — and passes it as `input.correlation` to `evaluateRouting` on every dispatch, so the decision/cache/attempt events append to the chain (MRC-02's emission path, `dispatch/src/routing-eval/index.ts:303-353`). `executeDispatch`'s Stage-C draft keeps minting fresh `sessionId`/`runId` (`:544-547`; the w4-p0 AC4 lineage contract is preserved). `CORRELATION_MISMATCH` continues to refuse a forked chain (`:534`).
4. **Named test-contract change.** The literal `000002-C-dispatch-order.json` expectations in `dispatch/tests/approval-cli.test.ts:410,:479,:485,:519,:798`, `dispatch/tests/mutation-scope.test.ts:57`, `dispatch/tests/root-guards.test.ts:315-318`, and `dispatch/tests/w4-p0-correlation-lineage.test.ts:333,:375,:422` are **replaced by the tip-derived contract**: the returned `receiptLocator` names the receipt actually written at the tip, and the assembled chain asserts the C1 invariant below. These are contract assertions evolving with a named contract item (the slot is no longer a constant), not incidental pins; every assertion is strengthened, none deleted in substance.
5. **The invariant (state it in the code comment and prove it by control):** *one chain per parcel, keyed by `correlation.workflowId`/`correlationId` (`checkSharedCorrelation`, `receipts/src/validator.ts:158-178`; the fork refusal `dispatch/src/routing-eval/index.ts:534`); the Stage-C `DispatchOrder` receipt and the routing event entries coexist on that chain with sequence values exactly `0..M-1`, contiguous, no gaps and no duplicate sequences (`checkSequenceContiguity`, `receipts/src/validator.ts:107-127`), each entry's `prevHash` pointing at its immediate predecessor's `hash` (`:129-155`) — i.e. every chain this parcel produces is `validateChain`-valid (`:181`), and the DispatchOrder is always the tip entry at its write time.* A reserved-but-later-filled slot is explicitly rejected as a design (it would introduce a gap whenever events land in between — contiguity has no gaps by construction).

### C3 — The dispatch gate (D8 semantics at the walk) — end-to-end F1/F2 closure

1. **Where:** the tier walk of `evaluateRouting` (`dispatch/src/routing-eval/index.ts:649`, *"7. Walk allowlist tiers in policy order; find first eligible model"*) — the walk order itself is untouched. **One predicate implementation:** the per-binding modality/thinking evaluation (the R2 D8 block `routing-policy/src/pi-resolver.ts:454-539`) and the context evaluation (the R4 block `:569-601`) are extracted into an exported pure function in `routing-policy/src/pi-resolver.ts`, called by **both** `evaluateCandidate` (behavior-identical — proven by MRC-03's suite passing unchanged) and the dispatch gate; `expertiseNarrowing`'s decision core (`:790-844`) is reused the same way. The walk's model→facts lookup follows `piModelContractFor`'s matching rule (`:844`): an `openrouter` binding whose `model` equals the walk's candidate id; a candidate with no such binding has **unknown** facts (evidence absent).
2. **Evidence rules (per requirement; the gate FILTERS within the walk order, never reorders — D3 `charter.md:188`, D4 `:189`):**
   - **Input modality.** When the effective set is the baseline `['text']` (declared or omitted — D8 makes them equivalent), no modality capability claim is made and the pre-existing selection is preserved byte-for-byte (the shipped AC4 contract, `dispatch/tests/routing-eval.test.ts:104-117`: text boilerplate selects `nvidia/nemotron-3.5-lightning`). When the effective set includes `image`: a candidate with **declared** facts missing a required modality is filtered with `INPUTS_INSUFFICIENT`; a candidate with **unknown** facts is filtered with `INPUTS_UNKNOWN` (D2/a54: a model-side fact is never guessed — selecting an unknown-fact model for `image` is exactly defect F1, `charter.md:114`). Never a silent downgrade.
   - **Thinking level (the resolved level is always known).** A candidate with **declared** `thinking_levels` missing the resolved level is filtered with `THINKING_LEVEL_UNSUPPORTED` (*"A model lacking the requested thinking level refuses rather than silently downgrading"*, `charter.md:193`); a candidate with **unknown** support is **not** filtered — the resolved level is carried and enforced where supported (*"enforces the resolved thinking level where supported"*, `charter.md:227`) — this asymmetry is the charter's own qualifier and is asserted by control.
   - **Context floor.** Only when `min_context` is declared: a candidate with **declared** context facts below the floor is filtered with `CONTEXT_INSUFFICIENT`; **unknown** facts filter with `CONTEXT_UNKNOWN` (a floor is a hard correctness bound — strict). Absent `min_context` = no floor, no predicate.
   - **Expertise narrowing.** Only when `expertise` is declared: the `expertiseNarrowing` decision (`routing-policy/src/pi-resolver.ts:790-844`) applies with its exact semantics — non-shadow entries for `(routing_class, expertise)` narrow the already-eligible set **preserving order**; no entry = no narrowing (never invents a preference); narrowed-to-empty = `EXPERTISE_BINDING_UNSATISFIABLE`; a dangling ref = `EXPERTISE_BINDING_DANGLING_REFERENCE`; shadow entries never narrow (RCM-P9 boundary). The walk maps the narrowed binding/candidate refs to its model ids via the C3.1 lookup rule.
3. **Failure shape.** When the gate leaves zero selectable candidates across all tiers, `evaluateRouting` throws a typed `RoutingError('REQUIREMENTS_UNSATISFIABLE', …)` whose detail carries the named refusals (name + detail per candidate); `prepareDispatch` maps it to a typed `DispatchError('REQUIREMENTS_UNSATISFIABLE', …)` (new code in the union at `dispatch/src/approval-cli/index.ts:45-57`), preserving the names — exit criterion 4's *"refuses with a typed error naming the unsatisfiable predicate"* (`charter.md:258-260`).
