# Standing Constraints — included by reference in every dispatch kickstarter

Every builder and reviewer kickstarter includes this file by reference (one line: "Standing constraints apply — `STANDING-CONSTRAINTS.md`"). Each rule below was earned on a real defect in this Line's own history; this file ships without the provenance citations, since this repo's own lessons ledger starts empty. Coordinator-side rules (shell discipline, closure checks, pre-PR gates) live in the coordinator's own operating documents, not here.

## Builder — universal

1. **Typed try-catch at every external boundary a public API exposes.** Every external call (third-party library, runtime I/O, network) reachable through your module's public API is wrapped in try-catch and rethrown as the module's own typed error class. Loads and writes both count; "never happens in practice" is not an exemption. Worked example: a module wraps every internally-thrown error in its own typed error class, but one exported function calls an external parser directly on unvalidated input — the parser's own exception type escapes uncaught the first time it receives malformed input, breaking every caller's catch clause that expects only the module's typed error.
2. **Seams your tests never exercise return `unknown`.** If a fetch/adapter seam is injected/mocked in every test and its real implementation never runs in the suite, its return type is `unknown` (or a raw parsed type) — never a confident cast to the domain type the tested code consumes. Normalization/validation happens explicitly at the boundary, where it can later be tested against a real response. Worked example: an adapter is typed to return `UserProfile` and every test supplies a hand-built `UserProfile` mock; the real HTTP call is never exercised, so a field the live API actually omits under a known condition silently becomes `undefined` at runtime with no test ever able to have caught it.
3. **Default-deny gates test every structural invariant independently.** A gate parsing a `SEGMENT-SUFFIX` token ships one test per invalid shape: no delimiter, delimiter at position 0, empty prefix, empty suffix — all rejected. Checking one property while assuming the rest is default-deny-with-exception, not default-deny. Worked example: a gate tests only "rejects a token with no delimiter" and passes; a token with an empty prefix (`-suffix`) or an empty suffix (`prefix-`) is never independently exercised and both slip through as accepted.
4. **Sanitize interpolated external data before emission into any line-based protocol.** Log sinks, chat/notification messages, CI annotations, terminal escapes: the protocol's delimiter (newline, `::`, `\x1b`) is an injection vector if it can appear in the data. Strip/replace before it enters the template, regardless of how "trusted" the source seems. Worked example: a notification template interpolates a user-supplied field directly into a single-line log/annotation format; the field contains an embedded newline and the protocol's own delimiter sequence, which splits the emitted line into two records and forges a second, attacker-controlled entry that downstream tooling parses as if the sender had produced it.
5. **Linear-time string handling when parsing untrusted text.** Required CI scanners (polynomial-ReDoS — regular-expression denial-of-service — detectors) are one verification net among several this Line runs (alongside type-checking, unit tests, and manual review) and the one most likely to fire only after assembly, late enough that a hostile-input defect ships before it is caught — write linear-time regexes/string ops up front and pin them with hostile-input tests rather than relying on that scanner to catch it first. Worked example: a validator uses a nested-quantifier regex against user-supplied text; a crafted input of a few hundred repeated characters drives the backtracking engine into exponential time, hanging the process on a single request until a scanner run days later flags the pattern.

12. **Parcel-time freezes live in the deterministic pass, not the shipped suite.** A test asserting a file is byte-unchanged (or append-only) versus a moving `origin/main` proves *your parcel's* discipline — so it belongs in the coordinator's pre-merge closure checks (the `git diff` review run once, right before merge) and dies with the parcel. If a file needs permanent protection, pin the invariant (export set, schema shape, frozen union) — never the bytes, which encode incidental order that tooling (organizeImports, formatters) legitimately changes. A shipped byte-pin hard-blocks every future chartered change to that file on its own PR.
    **Corollary — merge-idempotence:** any assertion whose *expected* value is a moving ref (`origin/main`, a merge-base, `HEAD~`) is a parcel-time check in a shipped test's clothing. It passes on the PR and can **invert on the merge commit**, reddening main while the PR was green — this is exactly what happens when a pin exempts a chartered addition on one side only and the target branch then gains the same addition independently. Either move it to the parcel-time pass, or prove it **merge-idempotent**: state what it evaluates to once your branch *is* the baseline, and evaluate it against that shape before opening the PR. Mutation testing cannot catch this — it proves an assertion binds against *today's* baseline, and this failure exists only in a future repository state.

13. **Allowlists and waivers pin identity, location, AND value.** A waiver keyed on a name alone can be squatted by a new artifact wearing that name; a waiver that suppresses a violation class regardless of value forgives future defects, not just historical ones. Pin all three axes (e.g. basename + parent directory + exact historical literal), and test each axis's refusal independently.

14. **A test that spawns a child test runner must prove the child actually ran.** A nested test-runner subprocess (or any subprocess whose job is to fail) inherits the parent's environment — a test-runner context variable in particular can make the child *silently skip*, so the assertion "this guard fails when I break it" passes while asserting nothing. Strip the inherited test-runner env vars in the child, and assert on the child's captured exit status AND its output naming the specific violation — never on the absence of a throw. Any paired reject-twin implemented as a subprocess is suspect until you have watched it go red.

15. **A parameterization must be proven with a value the old constant never held.** When you replace a hardcoded value with a caller-supplied parameter, tests that pass *the same value the constant had* cannot tell a working parameter from a fabricated one — the suite stays green when the implementation ignores the caller entirely. Assert a **non-default** value flows end-to-end, then re-run the ignore-the-parameter mutation and **watch your new test fail**. And never widen a gate, allowlist, or fixture guard to make that test convenient: assert through an ungated path and let the untouched gate refuse the value.

16. **An acceptance criterion (AC) that proves a prohibited thing is ABSENT must enumerate mechanisms, not patterns — and must report deferred instances rather than being narrowed to exclude them.** A grep for one or two known spellings of a behavior cannot establish "never does X": the same behavior can also arrive through an equivalent default-fallback expression, an indirect path-derivation idiom, or a subprocess call that inherits the same condition invisibly. List the *ways the behavior can be achieved*, write the check against that list, and assume one more spelling exists than you have found. If instances are deliberately deferred to a later phase, the check must **report them and still pass** as an enumerated exception — narrowing the pattern until they vanish is the same defect as a rule passing on zero matches, applied to your own audit.

17. **A count never determines coverage — enumerate identities and verify the enumeration against disk, in BOTH directions.** "Sweeps all N packages", "both copies of X", "the three call sites": a count is a *summary of an enumeration* that decays silently the moment the enumeration changes, while still reading as authoritative. Write the identities (names, paths), make that list the authority, and check it against disk both ways — **an expected item missing is an error, and an item present on disk but not expected is also an error.** A stale count has, more than once, decided what got checked and been wrong, leaving an entire unit unswept by a green audit.
   **Corollary: an enumeration is an authority only once it RECONCILES with the total it replaces — publish the reconciliation, and treat any list that does not sum to its total as unverified. A per-item table has the *shape* of evidence in a way a bare number does not, so it invites less scrutiny while carrying more places to be wrong; one such table summed to a total that did not match the figure it was supposed to reconcile with, and the mismatch was carried forward as verified anyway — the table looked like evidence, so nobody re-checked it.**

18. **An exception is defined by the behavior it may NOT excuse, and its membership is pinned — never inferred from shape.** An exception meant to cover only a legitimate case sharing the prohibited behavior's *shape* (e.g. a file that is allowed to compute its own location because it genuinely needs to locate its own assets) was exploited: a *different* piece of code, doing the actual prohibited thing, was written to share that same shape — split across two intermediate variables inside a file that already carried the exemption — and the gate accepted it, reporting it as a legitimate instance of the excused case rather than catching it as a new violation wearing the exempted file's cover. Test for the prohibited behavior wherever it appears, however many intermediate bindings separate cause from effect, and pin exception membership by identity + location + value so no site can enroll itself. **A gate that certifies a violation as compliant is strictly worse than one that misses it** — it converts a defect into documented evidence of correctness, and it survives review because the report looks thorough.

19. **An absence-proving check publishes its unmodeled cases alongside its verdict, and names the control that carries the real guarantee.** Widening never converges: two successive implementations of one absence check were each beaten several ways, and the remaining evasions all arrived through binding renames and data flow that no syntactic analysis can follow. Close what your technique can close, then **state in the check's own output what it does not model** ("a violation spelled this way passes; this is a regression tripwire over modeled mechanisms, not a proof of absence"), and pin that statement with a test so it cannot be quietly dropped. Then say where the real guarantee lives — usually a *behavioral* control that does not care about spelling. **An unstated limit is what makes a gate a lie; a stated one makes it an instrument.**
   **Corollary: a MIS-stated limit is worse than an unstated one — it is the lie told out loud.** Scope every coverage claim to the specific mechanism it is true of, and re-verify it whenever the check gains a new detector. A banner claiming "concatenation cannot evade it" was true of the enforcing classes and false of a dynamic-import detector added beside them — and a reader who checks the banner is *told* the case is covered, so the false claim actively suppresses the scrutiny silence would have invited.

20. **Every pinned exception set asserts its own CARDINALITY and fails on mismatch — in BOTH directions.** Pin by identity + location + **position** + value, and assert how many members the set is permitted. An over-count is an enrollment (a new violation absorbed by a pin keyed on shape); an under-count is a stale pin aimed at a site that no longer exists. **A pin that admits an extra member is a pattern with a friendly name.** Add this the moment a pinned set is created, not after one is caught — separate launderings have each gotten in through a different unguarded axis. And "the test suite catches it anyway" is not a defense: the check run standalone is the artifact you report as evidence, and **a gate may not be correct only when a different gate is watching it**.

21. **User-facing strings are shipped artifacts and are in scope for every portability check you apply to code.** Error messages, usage text, remedies, and generated docs get grepped for repo-shaped paths, hostnames, and org names exactly like source does. A remedy reading "run the install command in `<this-repo's-own-package-path>`" sends a user in a different repo to a directory that does not exist there. If a portability gate refuses one of these strings, **reword it — do not pin an exception to preserve it**; that is accommodation, not a fix.
    **Environment assumptions are the same defect in prose, and no token check can see them.** A document stating an operating system, a shell, a package manager, or a version quirk that is true only of the machine it was written on will pass a forbidden-token scan and a reference check **by construction** — it names nothing to match. A template that tells every builder to use one specific shell is simply false in a repo set up differently, and the instruction is followed anyway because it reads as canon. **Anything true only of the machine you are writing on is a defect in an artifact meant for other machines.** Turn it into a placeholder the receiving team fills from their own environment, and remember the control here is a reader who is not on your machine, never a pattern list.

22. **Report only command results you actually ran — and treat "reasoning, not verified" as a finished answer, not a weakness.** A claim written in the register of having been executed, when it was not, is a defect independent of whether the conclusion happens to be correct — both because it survives review (the tell is confident specificity, not implausibility) and because it can co-occur with a genuinely hollow check (e.g. an acceptance criterion whose own verification command returns zero against the file it is meant to verify). Mark every factual claim you have personally run a command for; reword the rest so they do not read as measured, name what *would* verify them, and leave them unverified. A stated unknown is worth more than a confident number, and a fabricated number is the exact defect portability and provenance work exists to eliminate.

23. **A pin over a literal set is not a control over its class — so name the class it cannot see, in the same breath.** A pin written to catch one forbidden name is bypassed by a sibling name adjacent to it; widening the pin to a small explicit list, with an explicit "this list is not coverage" note, is then bypassed again by *vocabulary* — an opaque internal index (a stage code, an abbreviation, a role token) into a taxonomy the reader receiving the artifact does not have access to. No list of literal names models an opaque index, and no amount of widening the list would have. What works instead is a line-by-line read by someone with no prior exposure to the source system, plus a rule that separates self-explanatory nouns (which need no gloss) from opaque indices (which need a one-clause gloss naming what they refer to). Corollary to rules #19 and #20: when a check's coverage is a literal set, its output must state the class the set does not model, and any acceptance criterion resting on that check must say so too — otherwise the criterion claims a proof of absence that the check cannot deliver.
    **A CATEGORY set is exactly as fallible as a literal set, and fails the same way — by reading as exhaustive.** A check once permitted a reference if the named artifact was one the repo *receives* or one it *reads from somewhere else*; the first artifact to exercise it named a third kind, one the repo *produces itself at runtime*. The check flagged a correct reference and the check was wrong. A two-item taxonomy looks complete in a way a two-item pattern list does not, so it invites even less scrutiny. **When a check enumerates kinds rather than instances, state the basis of the enumeration and expect a kind you did not model** — and exercise it against a real artifact early, because the alternative is discovering the gap during the acceptance run that depends on it.

24. **Measure counts with `grep -c`, invoking the binary explicitly by its absolute path — never `grep -o … | wc -l`, and never a bare `grep` you have not confirmed is the one you think it is.** The piped form has been observed returning a wrong number, on at least one platform, from a compound command. Separately and more subtly: a bare `grep` invocation can resolve to a different binary than expected depending on shell configuration, and two runs of the identical command have disagreed with each other on the same file and pattern for exactly that reason — the fix was not the pipeline, it was invoking the explicit binary path. Treat every count as suspect until you have verified which `grep` you actually ran; redirecting to a file and measuring the file also works. This extends the standing rule against reading an exit code through a truncating pipeline to counts specifically, and the count case is worse: a plausible number invites no scrutiny at all.
    **And never let a diagnosis stand on a remedy that merely appeared to work.** The first version of this rule blamed the pipeline and prescribed a substitute command; the substitute happened to be correct in the case that was tested, so the wrong diagnosis looked confirmed and shipped. It only surfaced when a reviewer found the substitute failing too. **A wrong root cause with a working workaround is the most durable kind of wrong**, because nothing fails to contradict it — so when you fix something, be able to say what made it break, not merely what made it stop breaking.

25. **State the legal VALUES, or name the artifact that holds them — defining what a field means is not enough.** Someone filling in a field needs its domain, not its purpose. A document once explained clearly what a risk level was *for* while hedging its values as "typically" one of a few names — on a field whose value triggered a mandatory audit — and described a tier as "a stronger tier", which is not a value. **"e.g." and "typically" on a load-bearing field are the documentation equivalent of a gate that cannot fail:** they look like specification and constrain nothing. Close the enumeration, or name the file that is authoritative for it so the reader can resolve it there. This applies to every field your artifact asks somebody else to supply.


26. **Ask whether what the spec says accomplishes what the parcel is FOR — not merely whether your code does what the spec says.** A parcel's design can be internally consistent, carefully argued, and a complete no-op for the defect it exists to remove — for example, bounding a lookup by a set that provably never contains the value it needs, so the "fix" falls straight back to the behaviour it was meant to replace. Every test passes. **No test in a suite asks this question**, and a review that only checks conformance to the spec will not either. Before you implement, state in one sentence what would still be broken if your implementation were perfect — and if the answer is the thing the parcel is named after, stop and say so.

27. **Cite the command you actually ran and what it printed — never a command that WOULD have shown it.** A report can reach a true conclusion on invented evidence: naming a plausible-sounding command in support of something you believe true is the same defect as inventing an output, and it is harder to catch, because the conclusion survives scrutiny while the reasoning does not. The rule about reporting only results you ran is not a rule about conclusions — it is a rule about **the sentence that carries them**. If you did not run it, say what you did run, or say you reasoned it.

28. **A sweep or count takes an explicit path argument — give the *target* a path, not just the tool. An absence claim states the scope it was run at, and the command's scope and the claim's scope must match.** A search whose path is relative to the working directory can match nothing and exit as though it found nothing: a no-op is indistinguishable from a real negative, and "no matches" then becomes a verified-looking claim resting on a command that never scanned a file. Declaring a working directory in prose **documents** the dependency; it does not **remove** it, and the same failure recurs the moment a command is copied or re-run from elsewhere. A command anchored to an explicit path either gives the same answer everywhere or fails *loudly* — and a loud failure cannot masquerade as a negative, while a silent divergence can. This is the companion to the rule about invoking the tool by absolute path: that one fixes which binary ran, this one fixes what it looked at. Never let a blanket claim of invariance stand beside a counterexample; a guarantee containing its own exception withdraws trust from every command it covers.
30. **Never pass a credential as an argument to anything — verify it by presence, length, or an in-process read.** Argument parsers, type coercions, and stack traces quote what they reject, so a value handed across a command line can be printed by a layer you never intended to reach. An agent comparing two copies of an API key *by SHA-256, specifically to avoid printing it* named its helper `H`; `h` is a built-in alias for `Get-History`, the secret bound to `-Id`, and the binding error echoed the key in full — twice. The key had to be rotated, and a `.gitignore` hardening shipped the same hour was irrelevant, because nothing was committed: the leak was to a transcript, which no ignore rule covers. **A redaction technique whose failure mode prints the input is not a redaction technique.** Hashing was the right instinct; routing the value through a shell defeated it. Test presence as a boolean (`[bool]$env:NAME`), compare lengths, or hash inside a process that reads the variable itself and never receives it as a parameter. And if you find two copies of one credential, say so — two storage locations for one secret is a hazard on its own.

31. **A compatibility/probe label does not make a path non-live, and XOR is about property presence rather than truthiness.** Reject compatibility/probe mode again at the first irreversible execution boundary. Enforce mutually exclusive routing fields with own-property presence, and bind blank, whitespace-only, and explicit-`undefined` twins in tests.

32. **Discover a pinned structural set before applying its eligibility filters, then reconcile both sets independently.** Traversal first enumerates every structurally matching candidate in the complete required artifact; only afterwards may location, ownership, or value rules select eligible members. Assert required-artifact presence, raw-candidate cardinality, eligible cardinality, and exact values as separate failure axes. Include at least one composed negative where the expected eligible set is intact but an ineligible duplicate also exists — separate one-axis controls do not detect a discovery filter that hides the duplicate.

33. **Pin your working directory absolutely in every shell block, and print it before any command with an effect.** The shell tool's working directory **persists across calls and is not private to you** — you inherit whatever the dispatching coordinator's session last set, which may be a different repository. Your permission envelope does not protect you here: `deny` rules and `additionalDirectories` constrain what you may *touch*, not where a relative path *resolves*, so a bare `cd sub/dir` can silently land in another repo and a prose prohibition in your kickstarter will not stop it. Therefore: (a) the first statement of every shell block is an absolute location change to your assigned worktree, never a bare relative `cd`; (b) in that same block, before any command with an effect, print the resolved location — an unprinted check is not a check, and a location command whose output you never saw has told you nothing; (c) if the printed path is outside your assigned worktree, **stop and report** rather than correcting it and continuing; (d) treat any command whose own banner or output names a foreign path as a stop, and do not remediate inside a repository you were not authorized to write. Do not assert whether pre-existing damage there was yours if you have no clean baseline to compare against — say what you observed and let the coordinator, who may hold a session-start observation you lack, establish attribution.

34. **A parcel that creates a package under `plugins/foreman-line/` enrols it in every governed list before claiming completion, and the D19 audit is the first of them.** The verification package's D19 audit discovers packages from disk and checks them against `verification/src/ratified-packages.ts` in **both** directions: a new directory that is not in the list refuses the whole run (exit 2), and CI fails in packages your diff never touched. Six adversarial reviews cannot see this, because the list lives outside the diff — CI found it on GSO-P2 after review had passed, exactly as lesson #74 recorded from an earlier parcel. Therefore, when your spec's `surfaces:` add a new `package.json` under the plugin: (a) `ratified-packages.ts` must be in your `surfaces:` and you add the package name in alphabetical position (the header says enrolment is a ratification — if the surface is missing, **flag at Step 0**, do not add it unilaterally); (b) run the audit against the **real plugin root** (`npm run d19-audit -- <abs path to plugins/foreman-line>` from `verification/`) before your first completion claim and report its output — every site it reports in your package needs a ruling in `d19-audit.ts`, which is a coordinator amendment and a further declared surface, not a comment in your code; (c) do not assert "no enumeration surface exists" from the CI workflow alone — the workflow discovers dynamically, the audit does not. ## Builder — conditional

6. **Classifier/heuristic parcels:** fixtures MUST cover the naming conventions that dominate real codebases (camelCase, concatenated, abbreviated), not just the canonical/textbook form — and for a *safety* classifier, the under-detect (false-negative) direction gets the most fixtures.
7. **Compression/summarization-touching parcels:** probe content length before assembly. A content-compression tool in the session path silently no-ops — passes the content through unshortened, with no error — once it crosses a small fixed token threshold, so a build that looks like it "just needs a retry" is actually past a hard ceiling that will not move on a second attempt. Content above the threshold is a stop condition requiring a coordinator ruling, not a silent retry.

## Reviewer

8. **Hostile-input probing is licensed.** You MAY run small one-off scripts against the live process boundary; green ACs verify the fixture space, not the input space.
9. **Prose-only contracts: attempt the naive reading.** For a parcel whose contract is prose rather than code, "is this unambiguous?" is answered by implementing the wrong-but-literal reading and showing the text excludes it — not by confirming the intended reading is present.
10. **Post-review git-detection control.** Every review cycle ends with an assertion of no commits/dirty files in the reviewer worktree; the permission envelope is a layer, not the guarantee.
11. **Mutate the fixture to prove each assertion binds to its named invariant.** For any test whose name claims an invariant ("…chain…", "…rejects hostile…", "…inherits identity…"), read the validator it calls and confirm that function actually checks that property — then break the fixture in the named dimension and confirm the test fails. An invariant that lives in a *different* exported function than the one under test is not checked just because a sibling function was called. Passing is not evidence; failing-when-broken is.
